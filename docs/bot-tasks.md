# 主 Bot 派活（Bot tasks）

一次派活 = **主 Bot 在自己这一轮里，把一件或几件事交给名单上别的 Bot，等它们做完、拿到结论，
接着在同一轮里处理。**

人看到的是一段连贯的对话：

```
我：让 @客户经理 把 @Gmail 整理一下，再让 @财务 按它的结论核一遍账单
我的助手：好，先让客户经理扫邮箱，扫完再交给财务核账。
  ┌ 客户经理  ⟳ 正在执行：扫描 Gmail 收件箱，找出需要关注的邮件…
  └ 财务      ⏸ 等客户经理做完
  （客户经理做完 → 卡片换成它交回的结论；财务开始跑）
我的助手：两边都交回来了。汇总如下……
```

它和 [delegation.md](./delegation.md) 的子代理委派是两件事：

| | 子代理委派（`delegate_task`） | 派活（`assign_task`，本文） |
|---|---|---|
| 交给谁 | 一个新开的、干净的**自己** | 名单上**另一颗 Bot**（它有自己的人设、Skill、连接、记忆） |
| 跑在哪 | 同一席位的一条子会话 | 对方自己的席位、**对方的主会话**（人在它的对话里看得见这件活） |
| 谁能用 | 每颗 Bot | **只有主 Bot**（一人一颗，迁移 0057） |
| 同步还是异步 | 同步 | **同步**：工具一直等到所有派出去的活交回来 |
| 价值 | 上下文隔离 | **分工**——销售那颗有 CRM 连接，财务那颗有报表知识库，主 Bot 自己没有 |

---

## 1. 为什么是同步，以及谁在等

第一版是异步的：工具当场返回「已派出」，结论以一条消息回到主 Bot 的对话，主 Bot 在新的一轮里
处理。用下来的问题很具体：结论画成了「用户发的消息」，主 Bot 的处理被拆成几条互不相干的回复，
它要靠翻历史想起自己为什么派；多派几颗时，谁先回来谁先开一轮，没法「等齐了再汇总」。

改成同步之后，**等待的是主 Bot 的席位，不是 Gateway**：

```
主 Bot 的席位（assign_task 在这一轮里 await）
   │ POST /runtime/tasks           记一条，带上「我在等」的租约（waiterUntil）
   │ GET  /runtime/tasks/:id       每 2 秒问一次，顺手续租
   ▼
Gateway 的 bot_tasks（只记、只租、只收，不敲任何席位）
   ▲
   │ 目标 Bot 的席位（机器上的工人 / 桌面端里的本地 Bot）来领 → 发进它的会话 → 等它那一轮收口 →
   │ 把**最后一条回复**作为结论回报
```

Gateway 依旧不主动打进任何席位，也不挂长请求——这是第一版选异步的全部理由，同步方案一条都没破。

### 1.1 等的那一方没了怎么办

主 Bot 的席位在等的时候可能被重启（换版、机器重启）。工具的 await 跟着进程一起没了，而对方
那颗 Bot 还在干活。**结论不能丢**：

- 等的一方每次轮询续一次租（`waiterUntil`，60 秒）。
- 对方交回结论时：租还在 → 记成 `answered`，等的一方下一次轮询取走，记成 `done`；
  租过期了 → 走**兜底送回**：由主 Bot 的席位领一条 deliver 活，把结论作为一条「任务结果」
  消息发进主 Bot 的对话（就是第一版的做法），主 Bot 在新的一轮里处理。
- 已经 `answered`、等的一方却在取走之前没了：维护节拍把它转成兜底送回。

兜底送回是异常路径，正常情况下结论只出现在主 Bot 那一轮里。

### 1.2 人按了停止

工具收到中止信号，对没收场的每一条 `POST /runtime/tasks/:id/cancel`：还没被领走的直接作废；
已经在对方那边跑的**停不下来**（那是对方的一轮，人可以去它的对话里按停止），但它交回的结论
不再送回主 Bot。

## 2. 编排：串行、并行、串并混合

主 Bot 一次调用交一张小图，工具按依赖关系执行，**全部收场才返回**：

```jsonc
assign_task({
  tasks: [
    { id: "mail",  bot: "客户经理", instruction: "扫描 Gmail 收件箱，找出需要关注的邮件……" },
    { id: "crm",   bot: "销售",     instruction: "列出本周跟进中的客户……" },
    { id: "bill",  bot: "财务",     instruction: "按邮件里提到的账单核一遍……", after: ["mail"] }
  ]
})
```

- 没有 `after` 的一起开跑（并行）；`after` 写了谁，就等谁做完再跑（串行）；混着写就是串并混合。
- **前置任务的结论自动附在后一条的指令末尾**（「—— 前置任务交回的结论 ——」），对方看不见主 Bot
  的对话，不附的话「按邮件里提到的账单」它无从下手。
- **同一颗 Bot 的几条自动排队**：一颗 Bot 一条主会话，两件活同时发进去就是两轮抢着说话。
- 前置任务没做成，依赖它的那些**不跑**，记成「跳过」，原因写明是哪一条没做成。
- 一次最多 6 条。环、引用了不存在的 id、名单上没有的 Bot，整次不发生，原话告诉模型。
- 单条简写 `{ bot, instruction }` 照旧认。

回给模型的是每一条的状态和结论，按 `tasks` 里的顺序排（不按谁先跑完）：

```
[1/3 done · @客户经理 · 4m12s] 扫描 Gmail 收件箱……
  结论：……
[2/3 done · @销售 · 1m05s] 列出本周跟进中的客户……
  结论：……
[3/3 failed · @财务 · 0s] 按邮件里提到的账单核一遍……
  没做成：它那边还有一件转人工的事等着人处理（……）
```

**结论只取对方那一轮的最后一条回复。** 模型每调一次工具前常会先说一句「我先读一下收件箱」，
把这些过程话拼进结论只是噪音；那一轮的最后一条才是它交出来的东西。

等太久（默认 30 分钟，`SATUWORK_ASSIGN_WAIT_MS`）工具不再等，告诉模型哪几条还在跑、结论之后
会以「任务结果」消息送回来——走的就是 §1.1 的兜底送回。

## 3. 只有主 Bot 能派

三道门，每一道单独成立：

1. **工具表。** `assign_task` 只在目录下发了 `assignable`（可派的 Bot 名单）时进工具表，
   Gateway 只给**这个账号的主 Bot** 下发那份名单。换主 Bot 的那一刻目录指纹变，席位下一次
   探针就把工具换掉。
2. **接口。** `POST /runtime/tasks` 用席位票，body 里带 `fromBotId`；Gateway 查 `main_bots`，
   不是这个账号的主 Bot 一律 403。
3. **目标。** 得在名单上、不能是自己；对方那颗不是主 Bot，所以它没有 `assign_task`，派活只有一层。

外发闸放行 `assign_task`（和网页搜索、知识库同一类：出口在 Gateway 自己的控制面）。目标 Bot
那边不加任何限制，它收到的就是一条带身份的消息，每一次调用照样过它自己的边界。

## 4. 界面

**派出去的每一条，在主 Bot 的对话里画成一条「那颗 Bot 发的消息」**，插在主 Bot 派活那段话
和它接下来那段话之间：头像、名字是被派的那颗 Bot 的，内容随状态变：

| 状态 | 画什么 |
|---|---|
| 等前置 | 「等 @客户经理 做完」 |
| 正在执行 | 任务一句话 + 动画（这就是「哪个 Bot 正在执行哪个任务」） |
| 做完 | 它交回的结论，按 Markdown 画，长的折起来 |
| 没做成 / 跳过 / 已停止 | 一句原因 |

数据来自主会话里的 `bot/assign` 事件（同一个 id 会来多条，取最后一条）。界面折叠时遇到它就
**把主 Bot 的气泡断开**：派活前那段话一个气泡，任务卡一条条排在中间，主 Bot 拿到结论之后说的话
另起一个气泡。工具结果改为按 callId 认药丸，不受气泡断开影响。

目标 Bot 的对话里，那条指令带「主 Bot 派来的任务」角标；兜底送回那条带「任务结果」角标。

对话里的 `@名字`（人打的、主 Bot 回复里写的）一律就地画成点名药丸：Bot 用头像，连接器用图标。

## 5. 契约

### 5.1 `bot_tasks`（迁移 0058、0059）

```
status        queued → running → answered → done          正常路径
                              ↘ reporting → delivering → done   兜底送回（等的一方没了）
              cancelled（人按了停止）  failed（送不回主 Bot）
waiterUntil   等的一方的租约，每次轮询续 60 秒
cancelledAt   人按了停止的时刻；对方交回结论时据此不再送回
```

### 5.2 Gateway

| 接口 | 谁 | 做什么 |
|---|---|---|
| `POST /runtime/tasks` | 席位票（主 Bot） | 建一条，带上等待租约；403 不是主 Bot，404 目标不在名单，409 同一颗上一件没收场 |
| `GET /runtime/tasks/:id` | 席位票 | 取状态并续租；`answered` 的当场记成 `done` 交出结论 |
| `POST /runtime/tasks/:id/cancel` | 席位票 | 人按了停止 |
| `GET /runtime/tasks?sessionId=` | 登录票 | 这条会话派出去的那些 |
| `/worker/tasks/*`、`/runtime/local-tasks/*` | 机器票 / 本地 Bot 的席位票 | 领活、started、renew、finish（run 带回结论；deliver 只在兜底时出现） |

### 5.3 `bot/assign` 事件（主 Bot 的会话）

```ts
'bot/assign': {
  id: string                 // 这一条（tasks 里的 id，前面拼上 callId，会话内唯一）
  callId: string             // 派活的那次工具调用
  index: number; total: number
  taskId?: string            // Gateway 那一条；没发出去的（跳过、校验失败）没有
  bot: { id: string; name: string }
  instruction: string        // 主 Bot 写的原话（不含附上的前置结论）
  after?: string[]
  state: 'waiting' | 'running' | 'done' | 'failed' | 'skipped' | 'cancelled' | 'detached'
  result?: string            // done：对方最后一条回复；别的态：原因
  startedAt?: number; endedAt?: number
  at: number
}
```

`detached` = 等太久工具先回去了，结论之后走兜底送回。

## 6. 不做的

- **不做二层派活。** 目标 Bot 没有 `assign_task`。
- **不做撤回已经在跑的。** 对方那一轮停不下来；人可以去它的对话里按停止。
- **不做跨账号。** 派活不出这个人的名单。
- **不做进度。** 对方跑着的时候只画「正在执行」和动画，不转播它的每一步——想看就去它的对话里看。
