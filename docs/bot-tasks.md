# 主 Bot 派活（Bot tasks）

一次派活 = **主 Bot 在自己这一轮里，把一件或几件事交给名单上别的 Bot，等它们做完、拿到结论，
接着在同一轮里处理。**

人看到的是一段连贯的对话：

```
我：让 @客户经理 把 @Gmail 整理一下，再让 @财务 按它的结论核一遍账单
我的助手：好，先让客户经理扫邮箱，扫完再交给财务核账。
  ┌ 客户经理  ⟳ 正在执行：扫描 Gmail 收件箱，找出需要关注的邮件…
  └ 财务      ⏸ 等客户经理做完
  （客户经理做完 → 卡片换成它交回的结论；财务开始跑）
我的助手：两边都交回来了。汇总如下……
```

它和 [delegation.md](./delegation.md) 的子代理委派是两件事：

| | 子代理委派（`delegate_task`） | 派活（`assign_task`，本文） |
|---|---|---|
| 交给谁 | 一个新开的、干净的**自己** | 名单上**另一颗 Bot**（它有自己的人设、Skill、连接、记忆） |
| 跑在哪 | 同一席位的一条子会话 | 对方自己的席位、**对方的主会话**（人在它的对话里看得见这件活） |
| 谁能用 | 每颗 Bot | **只有主 Bot**（一人一颗，迁移 0057） |
| 同步还是异步 | 同步 | **同步**：工具一直等到所有派出去的活交回来 |
| 价值 | 上下文隔离 | **分工**——销售那颗有 CRM 连接，财务那颗有报表知识库，主 Bot 自己没有 |

---

## 1. 为什么是同步，以及谁在等

第一版是异步的：工具当场返回「已派出」，结论以一条消息回到主 Bot 的对话，主 Bot 在新的一轮里
处理。用下来的问题很具体：结论画成了「用户发的消息」，主 Bot 的处理被拆成几条互不相干的回复，
它要靠翻历史想起自己为什么派；多派几颗时，谁先回来谁先开一轮，没法「等齐了再汇总」。

改成同步之后，**等待的是主 Bot 的席位，不是 Gateway**：

```
主 Bot 的席位（assign_task 在这一轮里 await）
   │ POST /runtime/tasks           记一条，带上「我在等」的租约（waiterUntil）
   │ GET  /runtime/tasks/:id       每 2 秒问一次，顺手续租
   ▼
Gateway 的 bot_tasks（只记、只租、只收，不敲任何席位）
   ▲
   │ 目标 Bot 的席位（机器上的工人 / 桌面端里的本地 Bot）来领 → 发进它的会话 → 等它那一轮收口 →
   │ 把**最后一条回复**作为结论回报
```

Gateway 依旧不主动打进任何席位，也不挂长请求——这是第一版选异步的全部理由，同步方案一条都没破。

### 1.1 等的那一方没了怎么办

主 Bot 的席位在等的时候可能被重启（换版、机器重启）。工具的 await 跟着进程一起没了，而对方
那颗 Bot 还在干活。**结论不能丢**：

- 等的一方每次轮询续一次租（`waiterUntil`，60 秒）。
- 对方交回结论时：租还在 → 记成 `answered`，等的一方下一次轮询取走，记成 `done`；
  租过期了 → 走**兜底送回**：由主 Bot 的席位领一条 deliver 活，把结论作为一条「任务结果」
  消息发进主 Bot 的对话（就是第一版的做法），主 Bot 在新的一轮里处理。
- 已经 `answered`、等的一方却在取走之前没了：维护节拍把它转成兜底送回。

兜底送回是异常路径，正常情况下结论只出现在主 Bot 那一轮里。

### 1.2 人按了停止

**派出去的活跟着立刻停。** 工具收到中止信号，对没收场的每一件 `POST /runtime/tasks/:id/cancel`：

- 还没被领走的：直接作废。
- 领走了、还没开跑的：领走的一方报 `started` 时被挡下，指令一个字都不发进去。
- 发进去了、但对方正忙，指令还在它的队列里排着（§7）：领走的一方撤掉队列里那一条
  （`DELETE /api/sessions/:id/queue/:queueId`），记成已停止。对方的对话里一个字都不留。
- 已经在对方那边跑的：领走它的一方（机器上的工人 / 桌面端的本地 Bot）**每 2 秒续一次租**，续租的回复里带着
  `cancelled`。一看到就调对方席位的「中止当前这一轮」（`/api/sessions/:id/abort`），那一轮以 aborted 收口，
  报上来记成已停止；中止发出去 15 秒还没收口就不等了，照样记已停止。

老席位会把派活那条指令插进对方一轮正在跑的对话里（人正在和那颗 Bot 说话，插话 steered）。那一轮是人
自己的，停掉会把人的活一起砍掉——这时只放弃它的结论，不中止。新席位不再插话，见 §7。

### 1.3 人在目标 Bot 那边按了停止

人在被派的那颗 Bot 的对话里按了停止，那一轮以 `aborted` 收口，领走它的一方如实报上来。这是人明说
**不要它做了**，不是它没做成，所以分开记：

- Gateway：`runKind` 记 `aborted`，结论写成「已停止：有人在它的对话里把这一轮停了，这件活作废（别重派、
  别自己接着做；要不要重新做问人）」。主 Bot 这边按的停止另有 `cancelledAt`，记成 `cancelled`，不走这里。
- 主 Bot 的派活工具：这一件标成**已停止**（`cancelled`，卡片上灰色「已停止」，原因一行写「有人在 @设计师
  的对话里把它停了」），**同一次派出去的整批跟着停**：在跑的走和主 Bot 这边按停止同一条路（cancel → 领走的
  一方中止对方那一轮），等着的直接作废，都记成已停止、原因写「跟着停了：同一批里 @设计师 那边有人按了停止」；
  已经做完的结论留着。回给模型的那段明说这几件作废：不要重派，也不要自己接着做，如实告诉人哪件被停、
  哪些跟着停了，要不要重新做由人决定。
- 主 Bot 没在等（等太久先回去了，§1.1）：兜底送回那条的标题是「@设计师 那边停止了」，正文同上。

为什么整批停：同一次派出去的几件是同一件事拆开的，人在其中一颗那边按停止，是在说「这件事别做了」；
剩下的接着跑，做出来的只是一件被叫停的事的其余部分，还占着别的 Bot。

## 2. 编排：串行、并行、串并混合

主 Bot 一次调用交一张小图，工具按依赖关系执行，**全部收场才返回**：

```jsonc
assign_task({
  tasks: [
    { id: "mail",  bot: "客户经理", instruction: "扫描 Gmail 收件箱，找出需要关注的邮件……" },
    { id: "crm",   bot: "销售",     instruction: "列出本周跟进中的客户……" },
    { id: "bill",  bot: "财务",     instruction: "按邮件里提到的账单核一遍……", after: ["mail"] }
  ]
})
```

- 没有 `after` 的一起开跑（并行）；`after` 写了谁，就等谁做完再跑（串行）；混着写就是串并混合。
- **前置任务的结论自动交给后一条**（「—— 前置任务交回的结论 ——」），对方看不见主 Bot
  的对话，不附的话「按邮件里提到的账单」它无从下手。它走 `POST /runtime/tasks` 的 `context`
  字段、存进 `bot_tasks.context`（迁移 0061），**不拼进指令**：指令限 4000 字，前置结论另限
  16000 字（每条先截到 6000、几条合计压在 15000 以内）——结论是对方写的，长短由不得主 Bot，
  共用一个上限的话前置交回稍长一点，后一件就派不出去。
- **同一颗 Bot 的几条自动排队**：一颗 Bot 一条主会话，两件活同时发进去就是两轮抢着说话。排的先后按
  `after` 拓扑排出来的顺序（同一层按书写顺序），不按书写顺序——否则 `a 等 b` 而 a 写在前面时，隐含的
  「b 排在 a 后面」和显式的 after 互等到超时。这种排队**只管先后、不管成败**：前一件没做成，后一件照跑。
- 前置任务（显式 `after`）没做成，依赖它的那些**不跑**，记成「跳过」，原因写明是哪一条没做成。
- 一次最多 6 条。环、引用了不存在的 id、名单上没有的 Bot，整次不发生，原话告诉模型。
- 单条简写 `{ bot, instruction }` 照旧认。

回给模型的是每一条的状态和结论，按 `tasks` 里的顺序排（不按谁先跑完）：

```
[1/3 done · @客户经理 · 4m12s] 扫描 Gmail 收件箱……
  结论：……
[2/3 done · @销售 · 1m05s] 列出本周跟进中的客户……
  结论：……
[3/3 failed · @财务 · 0s] 按邮件里提到的账单核一遍……
  没做成：它那边还有一件转人工的事等着人处理（……）
```

**结论只取对方那一轮的最后一条回复。** 模型每调一次工具前常会先说一句「我先读一下收件箱」，
把这些过程话拼进结论只是噪音；那一轮的最后一条才是它交出来的东西。

等太久（默认 30 分钟，`SATUWORK_ASSIGN_WAIT_MS`）工具不再等，告诉模型哪几条还在跑、结论之后
会以「任务结果」消息送回来——走的就是 §1.1 的兜底送回。

## 3. 只有主 Bot 能派

三道门，每一道单独成立：

1. **工具表。** `assign_task` 只在目录下发了 `assignable`（可派的 Bot 名单）时进工具表，
   Gateway 只给**这个账号的主 Bot** 下发那份名单。换主 Bot 的那一刻目录指纹变，席位下一次
   探针就把工具换掉。
2. **接口。** `POST /runtime/tasks` 用席位票，body 里带 `fromBotId`；Gateway 查 `main_bots`，
   不是这个账号的主 Bot 一律 403。
3. **目标。** 得在名单上、不能是自己；对方那颗不是主 Bot，所以它没有 `assign_task`，派活只有一层。

外发闸放行 `assign_task`（和网页搜索、知识库同一类：出口在 Gateway 自己的控制面）。目标 Bot
那边不加任何限制，它收到的就是一条带身份的消息，每一次调用照样过它自己的边界。

## 4. 界面

**派出去的活和委派（子代理）画法一样：挂在主 Bot 派活那一轮的气泡里，一次 `assign_task` 一张卡，
一件一行。** 对方那一轮就是主 Bot 这一轮里的一段执行，人要看的是「这一轮派了谁、做到哪、交回了什么」。

每一行和委派卡的一行**是同一个东西**（gateway/ui/chat.js 的 `taskItemHtml`，见 docs/delegation.md §13），
只是任务前面多一个被派那颗 Bot 的头像和名字：第一行任务一句话 + 状态 + 读秒 / 步数，第二行随状态变，
点开是结论全文和过程。

| 状态 | 第二行画什么 |
|---|---|
| 等前置 | 「等 @客户经理 做完」 |
| 正在执行 | 「正在：web_extract https://…」+ 清单进度（领活方报的，没报就只说「正在做」） |
| 做完 | 结论第一句；点开是全文（Markdown） |
| 没做成 / 跳过 / 已停止 | 原因 |

**进度从哪来**：领走 run 那一步的一方（机器上的工人、本地 Bot）本来就读着目标那一轮的事件流，顺手
数出「第几步、正在调什么、清单做到哪」，随续租报给 Gateway（`bot_tasks.progress`）；主 Bot 的席位
每 2 秒轮询时取走，变了就再写一条 running 的 `bot/assign`。

**过程从哪来**：Gateway 交出对方跑在哪条会话（`runSessionId`），界面摊开时去那条会话取最近几轮，
只留这件活的那一段（core 的 `assignSlice`：从带着任务 id 的那条指令起，到它那一轮收口）——对方
是一颗有自己对话的 Bot，整段拿来，人会以为它和别人的来往也是这件活的一部分。

数据来自主会话里的 `bot/assign` 事件（同一个 id 会来多条，取最后一条）。界面折叠时把它挂在当前助手块的
`assigns` 上，和委派的 `tasks` 一样，**不断开气泡**。以前断开过：派活前一个气泡、任务卡单独成一条「那颗
Bot 发的消息」、拿到结论后另起一个气泡——主 Bot 被停掉时，收口落在断开后那个空块上，屏幕上剩一张孤零零的
「已停止」卡加一个空气泡。

目标 Bot 的对话里，那条指令画成**主 Bot 发来的一条消息**（左侧、主 Bot 的头像和名字），它那一轮默认
折在这张卡里，见 §7。兜底送回主 Bot 的那条带「任务结果」角标。

对话里的 `@名字`（人打的、主 Bot 回复里写的）一律就地画成点名药丸：Bot 用头像，连接器用图标。

## 5. 契约

### 5.1 `bot_tasks`（迁移 0058、0059）

```
status        queued → running → answered → done          正常路径
                              ↘ reporting → delivering → done   兜底送回（等的一方没了）
              cancelled（人按了停止）  failed（送不回主 Bot）
waiterUntil   等的一方的租约，每次轮询续 60 秒
cancelledAt   人按了停止的时刻；对方交回结论时据此不再送回
progress      领活方随续租报的进度（0060，JSON 文本），只给界面看
```

### 5.2 Gateway

| 接口 | 谁 | 做什么 |
|---|---|---|
| `POST /runtime/tasks` | 席位票（主 Bot） | 建一条，带上等待租约；403 不是主 Bot，404 目标不在名单，409 同一颗上一件没收场 |
| `GET /runtime/tasks/:id` | 席位票 | 取状态并续租；`answered` 的当场记成 `done` 交出结论；带 `runSessionId`、`progress` |
| `POST /runtime/tasks/:id/cancel` | 席位票 | 人按了停止 |
| `GET /runtime/tasks?sessionId=` | 登录票 | 这条会话派出去的那些 |
| `/worker/tasks/*`、`/runtime/local-tasks/*` | 机器票 / 本地 Bot 的席位票 | 领活、started、renew（可带 `progress`，形状不对的当没报）、finish（run 带回结论；deliver 只在兜底时出现）。本地 Bot 共用一个领活身份 `desktop:<账号>`，桌面端却是一颗一个进程：领活带 `?botId=`，只交这一步要敲它的（run 看目标、deliver 看主 Bot）；领到了不是自己的（老 Gateway）不碰，租约到期放回去 |

### 5.3 `bot/assign` 事件（主 Bot 的会话）

```ts
'bot/assign': {
  id: string                 // 这一条（tasks 里的 id，前面拼上 callId，会话内唯一）
  callId: string             // 派活的那次工具调用
  index: number; total: number
  taskId?: string            // Gateway 那一条；没发出去的（跳过、校验失败）没有
  bot: { id: string; name: string }
  instruction: string        // 主 Bot 写的原话（不含附上的前置结论）
  after?: string[]
  state: 'waiting' | 'running' | 'done' | 'failed' | 'skipped' | 'cancelled' | 'detached'
  result?: string            // done：对方最后一条回复；别的态：原因
  runSessionId?: string      // 对方那一轮跑在哪条会话，界面「看过程」去那里取
  progress?: { steps: number; tool?: { name: string; detail?: string }; todo?: { done: number; total: number; now?: string } }
  startedAt?: number; endedAt?: number
  at: number
}
```

`detached` = 等太久工具先回去了，结论之后走兜底送回。

## 6. 不做的

- **不做二层派活。** 目标 Bot 没有 `assign_task`。
- **不做跨账号。** 派活不出这个人的名单。
- **不做进度。** 对方跑着的时候只画「正在执行」和动画，不转播它的每一步——想看就去它的对话里看。

## 7. 目标 Bot 那边：一件活是一次性的一轮

派活跑在目标 Bot 的**主会话**里，人在它的对话里看得见这件活。可那一轮是替主 Bot 跑的差事，不是人和
它聊的天。2026-10-24 设计师那条会话：一件活跑到一半主 Bot 那边按了停止，人过一会儿在设计师的对话里说
「你好」，它又调了 21 次工具把那件作废的活接着做完——那一轮原样留在上下文里，模型看见的最后一件事是
「一件没做完的活」。

规矩是四条：

1. **一件活自己占一轮，不插话。** 目标 Bot 正忙（人在和它说话）时，指令排进它的队列，等那一轮收口再
   开自己的一轮；派活那一轮跑着时，人说的话、日常任务也排在它后面，不插进去。插进去的话，派活就成了
   人那一轮的一部分（停不掉、拆不出），人的话也会跟着派活一起被折叠、一起从上下文里消失。
   排队的行带着 `source`（谁派的、哪一件），跑起来和直接开轮一模一样。
2. **派活那几轮不进任何一轮的上下文。** `toAgentMessages` 开头去掉它们（`agent/task-turns.ts`）：
   指令本身、它那一轮从 `turn/start` 到 `turn/end` 的全部事件。人后面的对话看不见，下一件派来的活
   也看不见（每件活自足，指令里写全了），但派活那一轮自己看得见人前面聊的——销售那颗 Bot 知道人上周
   说过的客户，这正是派给它而不是派给子代理的理由。压缩的摘要走同一个函数，不会从摘要里漏回来。
   日志原样留着，翻历史工具照样翻得到。兜底送回主 Bot 的「任务结果」（`phase=result`）是主 Bot 自己
   要处理的，照常进上下文。
3. **停了就作废，不会复活。** 还在队列里的撤掉（§1.2）；在跑的中止，以 `aborted` 收口；不管哪种，
   因为第 2 条，后面没有任何一轮会再看见它。席位重启时，队列里排着的派活直接丢掉——等它结论的那一方
   跟着上一条命的事件流断了，已经按失败报回主 Bot，再跑一遍做出来的东西没人收。
   **清单也一样**：`todo` 清单是整条会话一份，派活那一轮列的步骤收口时放回开跑之前的样子
   （`tools/todo.ts` 的 restoreTodos）。不然活停了，输入框上面还挂着「正在执行 0/4」，而提示词叫模型
   「拿不准做到哪儿了就读一次 todo」——上下文里去掉了那一轮，它照样从清单里把作废的活读回来接着做。
4. **界面上折起来。** 指令画成主 Bot 发来的一条消息，名字旁边的小签跟着那一轮走：排队中 / 正在执行 /
   已完成 / 已停止 / 没收口（只有 `turn/start`、席位又说没在跑：上一条命死在半路）。它那一轮的回复和
   工具默认折在卡里，卡底下一个「展开过程 · N 次工具调用」，点开才露出来——一件活几十次工具调用，
   摊开会把人和这颗 Bot 自己的对话挤得找不着。**例外：那一轮里有没批的高风险确认、没人接的交接单时
   强制摊开**，小签写「等你确认」、不摆「收起」——确认卡挂在助手块上，折着人就看不见，主 Bot 只能干等
   到超时。批完、接完照常折回去。

第一个 `turn/start`**。以前数「前面还有几条别人的消息」，人在等待期间插的话不占一轮，一数就把自己那一轮
让给了别人。
