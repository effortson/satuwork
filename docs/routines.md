# 日常任务（Routines）

一条日常任务 = **一个 Bot 到点自己去做的一段指令**。它长在对话右栏里：上面是那块桌面，
下面是这颗 Bot 的任务清单，点进去是那一条的详情——名字、指令、什么时候跑、最近跑得
怎么样。

浏览器关着的时候它照样得跑。这一句决定了下面几乎所有的取舍。

## 1. 东西放在哪

| 东西 | 在哪 | 为什么 |
| --- | --- | --- |
| 任务定义、触发时间 | Gateway 的 `routines` 表 | 有库、有事务、有唯一的一份时间；席位随时会被重装，日程不能跟着一起没 |
| 每次跑的流水 | Gateway 的 `routine_runs` 表 | 「昨晚跑没跑」是这个功能能不能被信任的全部 |
| 跑出来的内容 | 席位的会话 JSONL | 和人自己发的消息一模一样，Gateway 不留正文（同 docs/gateway-runtime.md §2） |

归属是 **(accountId, botId)**，和席位同一个粒度：任务要把消息发进那个席位的会话，
落在别人名下的 Bot 上就没有会话可发。所以它跟着人走，不跟着公司走——别人看不见，
也删不掉（接口一律回 404，不是 403）。

## 2. 触发器

现在只有一种：`schedule`。存的是结构，不是 cron 串：

```jsonc
{ "kind": "schedule", "every": "hour|day|week|month",
  "at": "21:00", "weekday": 1, "day": 15, "tz": "Asia/Shanghai" }
```

- **不用 cron 串**，因为界面要能把它读成「每天 21:00」并且改回去。人写得出来的 cron
  串远比这套结构能表达的多，一旦存进去，那个编辑器就画不出来了。
- **`tz` 存在触发器里**，不是运行时去问机器。人设的是他自己的九点；机器时区是运维
  以后可能改的东西，让它决定已经设好的任务什么时候跑，等于某天早上所有人的日报都
  提前了八小时，而界面上那行字一个字都没变。
- 每月那一档，**该月没有这一天就落在最后一天**（31 号的任务二月照跑）。跳过和 28 号
  跑之间，后者才是人设它时的本意。
- **没写的字段给默认值，写了但不对的一律 400。** 「每天」那一档用不上 `weekday`，不该
  逼调用方填一个假的；但 `weekday: 7`（把周日写成 7 是最自然的手滑，这里 0 才是周日）
  要是也「给个默认值」，就会静静地变成周一——接口回 200、界面写着「每周一」，人只会
  以为自己记错了。

下一次是什么时候，算好了存在 `routines.nextRunAt` 上（`null` = 不排：停用了、没有
触发器、或者算不出来）。调度器因此一条 SQL 就能选出到点的那几条，不用把全部任务拉
出来逐个算。算法在 [gateway/src/lib/schedule.ts](../gateway/src/lib/schedule.ts)。

Slack 消息、Git 事件、Webhook 这些**还没有**。触发器在库里是个判别联合，加一种只是多
一个成员；界面上那颗「添加时间」到时候才变成一个选单——只有一种触发方式的时候摆一个
只有一项的选单，是让人白点一下。

## 3. 一次跑，四步

调度器在 Gateway 进程里，每 30 秒扫一次（`GATEWAY_ROUTINE_TICK_MS`，设 0 就不起；Vercel 上由
Cron 每分钟打 `/cron/tick`）。**Gateway 自己不跑**——它只抢、只记；发消息、等结果那一段在席位
旁边，由机器上的工人（§8b）或桌面端里的本地 Bot 来做。到点抢到一条之后，领走它的那一方：

1. 问席位这颗 Bot 的会话 id，报给 Gateway（`started`：Gateway 查有没有转人工挡着）
2. 读一下会话最后一条事件的 `seq`，作为等待的游标
3. **先挂上事件流，再发消息**——反过来的话，跑得快的那一轮会在流挂上之前就结束，
   然后这里等到超时，界面上是一个永远转着的圈，而事情其实早就做完了
4. 等到 `turn/end`，回报 Gateway（`finish`）：`completed` 记 `ok`，别的 kind 记 `error` 并写明是什么 kind

发出去的就是一条普通用户消息，走的是界面发消息那条路（`/api/sessions/:id/messages`）。
所以模型花的钱照常落在账本上（docs/billing.md），审批、`@`、工具全都和人自己发的一样。

几个刻意的取舍：

- **抢是一条带旧值的 update**（`claimRoutine`）。升级换版那几十秒里新旧两代进程会同时
  在跑，没有这一句，那一刻到点的任务会发两遍。
- **不补跑**。停机四个小时，回来时补发四份日报没有任何人想要——下一次一律从现在往后算。
  迟到半小时以内照跑（那多半是一次部署重启，21:00 的日报 21:03 发出来没问题）；超过
  `GATEWAY_ROUTINE_LATE_MS`（默认 30 分钟）就**不跑这一次**，但在流水上记一条「错过了」。
  静静地跳过等于让人以为它跑过了；而全都补上，就是重启那一刻一次涌出来一大批。
- **指令还空着就不跑**。界面上点「+」建出来、还没写内容的那条任务，不拦的话会每天发一次
  空消息、被席位以 400 顶回来、留一条红的。手动试跑那条路在接口上就回 400，两边一致。
- **等的是自己那一轮**。游标是发消息之前取的，中间隔着两跳 HTTP；人正好在这时候和这个
  Bot 说着话的话，他那一轮的收口会先到。所以按发消息那一跳的回话分两种走法：`steered`
  （话被插进正在跑的那一轮）认下一条 `turn/end`，否则先等一条 `turn/start` 记下轮号，
  只认这个轮号的收口。

跑砸了的那一次，会在 5 / 15 / 30 分钟后自己再来三次（见第 8 节）。

上一次还没跑完的，这一次直接跳过：同一个会话里两轮抢着说话，出来的东西谁也不认。

**这条会话上有一件转人工的事还等着人处理时，这一次也跳过**（`blocking` 的交接单，见
[handoff.md](./handoff.md)）。不拦的话，一件卡住的事会每小时重跑一遍、每小时开一张新单、
每小时往群里推一次通知——而人还没来得及处理第一张。跳过的那一次在流水上如实写明原因：
静静地不跑，和「跑了但什么都没做」在界面上长得一模一样。

## 4. 用哪个模型跑

每条任务自己选一个（`routines.modelRole`），**默认是 daily**：

| 选择 | 到点了用什么 |
| --- | --- |
| `daily`（默认） | **不覆盖**——这颗 Bot 平时聊天用的那个模型 |
| `utility` | 平台钉的 utility 模型 |

默认落在 daily，是因为人交代一件到点去做的事，期待的是「和我自己问它时一样的水平」；
定时任务跑出来的东西又比聊天更少有人当场复核，拿便宜那一档跑、再让人事后发现质量差
一截，这笔账不划算。每天都跑、活又简单的那种（日报、提醒），界面上拨到 utility 就是。

（早先默认是 utility。改默认只影响**新建**的任务：老任务在库里存着明确的 `utility`，
照旧按它跑，不会被悄悄换成更贵的那一档。）

`daily` 那一档写的是「跟平时一样」，**不是「钉到平台的日常模型」**。人在对话框里给这条
会话换过日常模型的话（docs/model-choice.md），定时任务跟着换过之后的那个——人选这一档，
要的正是「和我自己问它时一模一样」。（都没指定时回落到平台日常模型，见 `lib/catalog.ts`
的 `defaultBotModel`。）

**发给席位的是角色名，不是 provider + model。** 席位手上已经有平台下发的那两个角色
（目录里的 `models.{daily,utility}`），让它自己查一次就够了。反过来把具体那一对从
Gateway 发过去，等于给 `/api/sessions/:id/messages` 开一个「这一轮用哪个模型」的入口
——而那条路浏览器也走得通，于是任何人都能借它绕开管理员放开的白名单。角色名只有两种
值，绕不出什么去。`daily` 那一档干脆什么都不发：它的意思就是席位不带覆盖时的行为。

**压缩一律按这颗 Bot 自己那个模型的窗口算，不按这一轮钉的那个。** 压缩不是一轮的私事：
它把旧的那段换成摘要**写进会话日志**，而日常任务发消息进的，正是人和它聊天的那条会话
（一个 Bot 一条，见席位的 `ensureSession`）。按钉上的模型算的话，一条选了 utility 的
任务会拿那个便宜模型的小窗口去压人的聊天记录——人什么都没做，第二天回来上下文就没了，
摘要还是那个便宜模型写的。

那么钉的模型自己装不下这条会话怎么办？**这一轮退回 Bot 自己的模型**。剩下的两条路
都站不住：照发会被 provider 以超长顶回来，那条任务从此每天记一条 error；压到它的尺寸
就是上面那件事。退回去只是这一次贵一点，而它跑成了，人的上下文一个字没动。

四处**故意不保证**：

- **席位取不到 utility 就照旧跑**（还没拉过目录、或者平台压根没配）。省钱是这个开关
  的目的，不是它的前提——为它把一条本该跑起来的任务顶回去，是拿正确性换便宜。日志
  里留一行 warn：静静地按原模型跑，和真按 utility 跑，在会话里长得一模一样，而两者
  的账单差着一个数量级。
- **会话太长装不进 utility 的窗口时也照旧跑**（上面那一段）。同样留一行 warn——不然
  「这条任务怎么没省下钱」查无可查。
- **话被插进正在跑的那一轮时不生效**（人正好在和这个 Bot 说话，见第 3 节的 `steered`）。
  那一轮的模型在开跑时就定了，换不了；而为此另起一轮，等于让两轮在同一条会话里抢着
  说话。
- **旧版席位当它不存在**。`modelRole` 是发消息那条路上多出来的一个字段，认不出来的
  席位原样忽略，那几条任务照旧按 Bot 自己的模型跑，直到它换上新版。同样不拦：为一个
  省钱的字段把整条定时任务停掉，不划算。

不进审计。审计那一栏只记两件事——这个 Bot 会不会自己动、它自己动的时候做什么（见
第 6 节）；换模型是钱和质量的旋钮，改一次记一行，会把真正要紧的那两行淹掉。花了多少
钱的真相在账本里（docs/billing.md），那里本来就按模型分得清清楚楚。

## 5. 进程重启

跑着的那一轮不在 Gateway 进程里，Gateway 重启不影响它：领走的那一方按租约续命，Gateway
回来接着看租约。真正会留下孤儿的是两种「没人管的 `running`」：

- **工人领走了、进程死了没人续**：租约到期，每一轮扫描（`sweepLeases`）记成「机器没回报」并排补跑。
- **试跑登记了、一直没人来领**（机器关着、工人没起来、桌面端没开）：隔 `GATEWAY_ROUTINE_PICKUP_MS`
  （默认 3 分钟）没人领，`sweepUnclaimed` 记成 error 把话说明。不收的话那个圈永远转着，并发判据
  也一直认为它还在跑，这条任务从此再也跑不起来。

两条各看各的格：一条看 `leaseUntil` 到期，一条看 `leaseUntil` 为空且登记太久。

## 6. 审计

进审计的只有两件事：**这个 Bot 会不会自己动**（`routine.create` / `routine.delete` /
`routine.active`），以及**它自己动的时候做什么**（`routine.update`，带指令的头 200 字）。

改名字不记。这一栏要是被每一次失焦保存刷满，真正要紧的那两行就淹了。指令留一段而不是
只留一个 id，是因为审计那一屏要回答的正是「这个 Bot 昨晚为什么自己发了那封信」——答案
写在指令里；留一段而不是全文，是因为审计不是内容库（见 gateway-runtime.md）。

「上一次跑成没跑成」不在审计里，在 `routine_runs`。两张表回答的是不同的问题：一个是
「谁改了什么」，一个是「它昨晚干成了没有」。

## 7. 界面

`gateway/ui/pages-routines.js` 一个分片，挂在右栏里（`render.js` 的 `pageAside`）。

点开一条时整栏换成详情，**但上面那块桌面只是被 `hidden`，不是从 DOM 里拿掉**：它是
一条 VNC 连接，卸一次就断一次（见 `chat.js` 的 `syncDesktop`）。藏着的时候它的
`getBoundingClientRect` 全是 0，常驻层自己会判成不可见，连接照旧活着。

名字、指令、用哪个模型**收在 `change` 上，不是 `input`**：保存要 render（列表那一行、
下一次的时间都跟着变），而 render 会把输入框换掉——边打边存等于每敲一个字丢一次焦点。

「跑完了没有」的真相在 Gateway，浏览器只能问：详情里**有一条正在跑**时每 4 秒问一次，
没有就把定时器停掉，不然一个开着的标签页会永远每四秒一个请求。

**问完了没变化就一下都不画**（`routineShot` / `routineListShot`）。`render()` 是整页重绘
（`#app` 的 innerHTML 整块换掉），而这一栏挂在对话页上——轮询只在有一轮正在跑的时候转，
于是「试跑的这几十秒」正好是聊天正文每 4 秒被连根拔起重建一次的几十秒：正在流式输出的
那段 Markdown 全部重渲染、图片重新加载、贴底状态（`data-touched` 在被换掉的那个节点上）
跟着丢，气泡下面那行读秒也被拆了重建。而这几十秒里这一栏其实什么都没变，那一行一直
写着「正在跑…」。按内容比一下再决定画不画，比在重绘里补各种保位置的补丁简单得多。

## 8. 跑砸了，自己再来三次

一次失败之后，隔 **5 分钟、15 分钟、30 分钟**各补跑一次，三次都不成就停下，等下一次
到点。

为什么值得做：定时任务失败最常见的原因不是这件事本身做不成，是**那一刻够不着席位**
——机器还没开、正好在换版、网断了一分钟。而现在的代价是一整天：今天的日报没有了，
下一次是明天九点。

为什么是退避而不是等距：能自己好的那类几分钟内就好了，所以第一次补得早；真没好，
那多半不是「再等五分钟」能解决的，越往后越该拉开距离——而不是每五分钟去撞同一堵墙，
每撞一次在会话里留一条红的。三次之后停，是因为再往下就成了「一整天都在重试」，而一件
连着四次都做不成的事，要的是有人去看一眼。

间隔在 `GATEWAY_ROUTINE_RETRY_MS`（毫秒的逗号串，只为把这几十分钟压到 e2e 等得起的
量级）。写坏了一律退回默认那三档——**不接受「配一个空表 = 关掉重试」**，那是个太容易
手滑出来的行为。

### 欠着的那次补跑存在哪

`routines.retryAt`（什么时候补）和 `routines.retryCount`（补到第几次了），**和排期的
`nextRunAt` 各占一格**。

不写回 `nextRunAt` 是要紧的：写回去的话，一次失败会把「每天 21:00」挪成「21:05」，
界面上那行「下一次」也跟着变——人看到的是自己设的时间被系统改掉了。也不放在
`routine_runs` 上：那张表只留最近 50 条，一条会被删掉的行不能拿来当调度状态。

调度器每一轮扫两遍：到点的那几条，和欠着补跑的那几条（`tickRetries`）。补跑那一遍
和到点那一遍有三处不同：

- **先看有没有在跑，再抢**（到点那遍是先抢后看）。抢到手就等于把 `retryAt` 抹掉了，
  而这一次又没跑成，那次补跑就凭空少了一回。留着不抢，等在跑的那一轮自己收场——跑成了
  它清掉这一串，砸了它排下一次。
- **迟太久（`GATEWAY_ROUTINE_LATE_MS`）的直接作废**，不像到点那遍还在流水上记一条
  「错过了」。停机四小时之后补一次四小时前该做的事，和补一份昨天的日报是同一件不该做
  的事；而那次失败本来就在运行记录里红着，不补不会让人以为一切正常。
- **指令被清空了就把这一串收掉**：这条任务现在什么都不做。

到点跑的那一次会把欠着的补跑一笔勾销（`claimRoutine` 一条 SQL 里做掉）——22:00 到点
的那次做的就是同一件事，21:00 那次失败排下的补跑已经没有意义了。

**这条任务从此不再自己动了，也一并清掉。** 判据是重算出来的 `nextRunAt` 是不是 null，
不是「有没有拨开关」——两条路都到得了这个状态，而它们在人那边是同一句话：

- 拨到停用
- **把时间一个不剩地删光**（界面上删掉最后一个触发器，发的就是 `triggers: []`）

少了后半句的表现最难看：21:00 那次失败排下 21:05 的补跑，人 21:02 把唯一那个时间删掉，
21:05 这个 Bot 照样自己把指令发了出去，而那一刻它在列表上写着「还没有设定时间」。重新
打开时也清，否则停用期间攒下的旧时刻会在打开那一瞬间就到点。

改指令、把时间从九点改成七点**不清**——那两下说的是「以后怎么跑」，这条任务还是会自己
动，而这次补跑欠的是刚才那一次。

### 哪些失败不补

`retryable` 问的是「再试一次有希望吗」，不是「它失败了吗」：

| 这一次的结局 | 补不补 | 为什么 |
| --- | --- | --- |
| 够不着席位、席位那一跳报错 | 补 | 正是重试最该管的那一类 |
| 那一轮以 `error` 收场 | 补 | 模型/工具那一跳砸了，再来一次常常就过了 |
| 人按了停止（`aborted`） | **不补** | 他要的就是别跑，五分钟后自己跑起来是最糟的回应 |
| 等结果超时 | **不补** | 那不是失败，是**结果不明**（第 5 节）——那一轮很可能还在席位上跑着，再发一条进同一条会话就是同一件事做两遍 |
| 有一件转人工的事挡着 | **不补** | 五分钟后它照样挡着，而每补一次就多一张单、多一次通知 |
| 「错过了这一次」 | **不补** | 那一次压根没触发，补它就是补跑（第 3 节说了不做） |
| 进程重启收掉的 `running` | **不补** | 同样是结果不明；而且重启之后 `nextRunAt` 已经是下一次了 |
| **手动试跑** | **不补** | 人就坐在屏幕前，他要的是看这一下成没成，不是接下来五十分钟里再自己跑三遍 |

「不补跑」（第 3 节）和「失败了重试」不矛盾，两句话说的是不同的事：前者是这一次**压根
没触发**，补上去只会在开机那一刻涌出一堆没人要的东西；后者是这一次**触发了、也确实去
做了、砸在了半路**，而人是奔着结果设的它。

## 8b. 由席位机器上的工人来跑

Gateway 要变成无状态的（[adr-gateway-vercel-neon.md](adr-gateway-vercel-neon.md)），「到点了去敲席位、
挂着流等 20 分钟」这件事就不能再在它进程里发生。机器协议 ≥ 7 时，那台机器上的任务改由机器
自己来领：

| 一步 | 谁 | 接口 |
| --- | --- | --- |
| 领活 | 工人凭 `smt_` | `GET /worker/routines/due` —— Gateway 在这里抢（同 §3 的规矩：空指令不跑、迟太久记「错过」、上一轮没完就跳过），登记一条 `running` 流水，带租约交出去 |
| 问能不能跑 | 工人拿到会话 id 之后 | `POST /worker/routines/:runId/started {sessionId}` —— Gateway 查这条会话有没有转人工挡着（§8 那条规矩不变），挡着就当场收成 error |
| 续租 | 工人每隔租约的三分之一 | `POST /worker/routines/:runId/renew` |
| 回报 | 工人等到自己那一轮的 `turn/end` | `POST /worker/routines/:runId/finish {kind}` —— `completed` / `aborted` / `timeout` / `failed` / 其余，怎么解释、补不补，规矩在 Gateway（`settleRun`），和它自己跑时一字不差 |

**Gateway 的调度器不碰归工人的任务**（`tickRoutines` 按席位所在机器的协议号分流）。
机器不够新（协议 < 7，还没有工人单元）时 Gateway **也不自己跑**：抢过来、在流水上记一条
「管家太旧，先升级」的 error，不补。以前那条「Gateway 自己打进席位等二十分钟」的路收掉了——
它在 Vercel 上走不通（函数一回响应就冻住），留着只会在流水上留一行没下文的 running。

**机器离线怎么记。** 以前是 Gateway 敲不到席位、记一条「实例还没上线」再排补跑。下沉之后
Gateway 不再去敲，改看租约：工人领走的流水带 `leaseUntil`，进程死了没人续，到点 Gateway 的
清扫（`sweepLeases`）记成「机器没回报」并排补跑——和「够不着席位」是同一种失败，补三次。

流水上因此多两格 `machineId` / `leaseUntil`（迁移 0039）。

**试跑**（`trigger = manual`）走同一条路：Gateway 只**登记**一条流水（`requestManualRun`）——
`machineId` 指向该来领的那一方、`leaseUntil` 空着——界面立刻拿到它转圈，工人下一趟 `due`
时连同到点的一起领走，那一刻租约才开始计。机器不在线、管家太旧、Bot 没部署，登记那一步就 409。

**本地 Bot（桌面端）**没有机器也没有工人：Gateway 连不到员工的电脑，`dueRoutines` 把它的任务排除在外。
由它自己的 Bot 进程来领（bot/src/local-routines，凭席位票打 `/runtime/local-routines/*`，只看得到自己账号
本地 Bot 的任务，流水上的 machineId 是 `desktop:<accountId>`），往自己的会话里发、等自己那一轮跑完、回报。
电脑关着、应用没开就没人领，Gateway 只是排着，不记「错过」。

**机器那一半**是 `satuwork-worker.service`（manager/src/worker/index.ts，见 manager/README.md
「席位工人」）：非 root、不持有任何凭据，经管家在回环地址上的中继口领活、跟本机 bot 说话。
一次跑的顺序：问会话 id → started → 读游标 → 先挂流再发消息 → 只认自己那一轮的 turn/end →
finish；期间按租约的三分之一续命，续不上（404）就停手。

## 9. Agent 内置工具

当前 Bot 有两把主代理专用工具：

| 工具 | 能做什么 |
| --- | --- |
| `routine_list` | 列出当前 Bot 的全部日常任务；按 id 或完整名字查看一条及最近十次流水 |
| `routine_manage` | `create` 新增、`update` 修改、`run` 立即试跑 |

工具只是 Gateway 现有六条接口的席位客户端，不在 Bot 本地复制定义、下一次运行时间或调度器。
因此右栏和 Agent 看到的是同一批记录，立即试跑也复用 `requestManualRun`，不会出现
“Agent 试跑走一套、页面试跑走另一套”的分叉。

### 9.1 权限

原接口同时接受登录 JWT 与席位票 `sat_`：登录票代表人在页面操作，席位票代表 Bot 调工具。
两者都只能碰创建这条任务的账号。席位票还要额外钉当前 `botId`：一个账号可以部署多颗 Bot，
而账号级席位票本身不能证明当前进程是哪一颗；只验 `accountId` 会让 A Bot 猜中 id 后修改 B
Bot 的日常任务。

新增、修改和试跑在审计或运行流水里照常留痕。由席位票发起的创建 / 修改在审计 detail 里带
`by: 'bot'`，页面操作带 `by: 'user'`。

### 9.2 什么时候调用

带截止时间的普通工作不是日常任务。“周四 18:00 前完成”本身不会创建后台安排；只有用户
明确说“每天九点”“每周五自动执行”“到时提醒”这类无人值守的重复或定时行为，才调用
`routine_manage`。新建时名称、指令、触发时间或时区缺一项就先问，不能替用户猜一个默认值。

修改现有任务可以先用 `routine_list` 核对。`triggers` 是整组替换，不是追加；立即触发只新增
一次 `manual` 流水，不改原排期。工具暂不提供删除——删除定义会连带移除运行流水，仍由人在
右栏明确操作。

### 界面上看得见

补跑的那几次在运行记录里挂一个「重试」的牌子，和「试跑」并列。**必须标出来**：不标
的话，一条每天都要补一次才成的任务，在那一列上就是一串正常的绿勾——而它其实每天都在
第一跳上摔一次。

还欠着补跑时，详情里在「下一次」下面多一行：「上一次没跑成，22:42 再试一次（第 1 次，
共 3 次）」。不写的话，人看到的只有一条红的记录，于是自己去点试跑——而十分钟后那次
补跑照样会跑，同一件事做两遍。

**排着补跑的那几分钟不轮询**（`routinePollWant` 只在真的有一轮在跑时才转）。等五分钟
每四秒问一次，为的是把一行字提前几秒换掉，不值当。
