# 子代理委派（Delegation）

一次委派 = **主席位把一件事整个交给一个新开的、干净的它自己，它跑完只交回一段话。**

[gateway-runtime.md §1](./gateway-runtime.md) 把「子代理」列进了「先不做」。这份文档是来把它
从那张单子上划掉的：和 gateway-runtime.md 冲突处以那一份为准，本文在它的席位模型、会话
事件、审计口径上**加一类东西**——不改席位边界，不改计费口径，不改 `@` 点名的语义。

**这件事的全部价值是上下文，不是并发。** 这一句决定了下面几乎所有的取舍。一件子任务的
*过程*——翻二十个文件、试三次命令、读回来两屏报错——对主对话是纯噪声，它只需要那一句
结论；而今天这些过程全都堆在唯一那条长会话里，一路把窗口顶到压缩线。并发和便宜模型是
顺带的好处，不是理由；把它们当成理由，就会做出一个「能同时跑三件事、但每件都做不对」的
东西。

前置阅读：[context-assembly.md](./context-assembly.md)（一次请求由什么装配出来）、
[handoff.md](./handoff.md)（一个有状态、要落盘的对象长什么样）、
[routines.md](./routines.md)（一条不面对人的执行路径要注意什么）。

## 1. 原来缺的是什么

| 原来就有的 | 原来缺的 |
|---|---|
| 一轮可以连着跑 120 步（`DEFAULT_MAX_STEPS`），长活干得完 | 那 120 步的过程**全部留在主上下文里**。一次「把日志翻一遍找出为什么昨晚失败」能吃掉三万 token，而结论只有两行 |
| 自动压缩兜着，撞不到窗口那堵墙（[context-assembly.md §6](./context-assembly.md)） | 压缩是**事后**补救：钱已经花过了，而且被压掉的是**主人自己说过的话**，不是那堆工具噪声 |
| 一次能调多个工具，模型自己会并行 | 并行的是**工具**，不是**任务**。「同时查三个供应商的报价」这种事只能一个一个来 |
| `utility` 这个便宜模型角色已经在目录里（`catalog.models.utility`） | 只有网页提取摘要在用。没有任何一条路能让主代理说「这段脏活你用便宜的跑」 |
| Skill、连接、工作区、边界都挂在席位上 | 没有办法开一份**干净的上下文**做一件事。让它评审自己刚写的东西，它看得见自己写的时候在想什么，于是评审必然是「我觉得挺好」 |

所以模型今天面对一件大活只有两条路：塞进这一轮（污染上下文），或者让人手动开一句
「先只做第一步」（把编排的活推回给人）。下面这一整套要修的就是这两条路之间那个空洞。

## 2. 从 Hermes 那份文档里借什么，不借什么

参考的是 Hermes Agent 的 `delegate_task`（`user-guide/features/delegation`）。它的骨架是对的：
**独立上下文 + 继承工具 + 只回摘要**。分歧全在边界上，而分歧的来源只有一个——它的子代理跑在
后台，我们的子代理跑在**一台员工正看着的席位上**。

| Hermes 的做法 | 我们 | 为什么 |
|---|---|---|
| 后台委派，立即返回 handle，完成后再交付 | **v1 同步**：`delegate_task` 这次工具调用真的 `await` 在那儿 | 异步交付要新造一条「把结果送回一条已经收口的会话」的路。routines 已经走过一遍，代价看得很清楚：结果落在**新的一轮**里，模型看不见自己当初为什么委派。见 §11 |
| 默认并发 3，超出返回工具错误 | 一次 `delegate_task` 里最多 3 条，一起跑 | 同步这一条把「席位级并发上限」白送了：一颗席位同时只有一轮在跑，那一轮里只有这一次调用 |
| 子代理默认换成便宜模型省钱 | **不给默认**：主代理按难易度**逐条**表态 `daily` / `utility` | 见 §8。默认省钱只在「子代理干的是机械活」时成立，而最值得委派的恰恰是过程很长的判断活 |
| `max_spawn_depth` 最高 3，可嵌套编排 | **定死 1**，叶子不能再委派 | 他们自己那段警告已经把理由写完了：3×3×3 = 27 个并发叶子。而我们一台席位只有一颗浏览器、一块屏 |
| 按名字列一张屏蔽表（`memory` / `code_execution` / `send_message`…） | **不列名单**，判据挂在工具自己身上（§6.1）；今天落下来只屏蔽 `delegate_task` / `escalate_to_human` | 内置工具集还在长，名单当天就会过期，而漏一条是静默的。我们不屏蔽 `terminal`：它有工作区边界和策略管道兜着，而且它是**交付通道**（§7.2），不是逃逸口 |
| 子代理没有墙钟超时 | **有**（§9） | 他们的委派在后台，超时无所谓；我们的主轮 `await` 在那儿，人对着一个转圈的图标 |
| 上下文严格隔离，只带项目上下文文件 | 隔离，**但给一把回主会话的只读检索手**（§6） | 隔离要防的是「两万 token 的历史进每一次子请求」，不是「不让它知道任何事」。同一条理由压缩那边已经用过：压缩不是丢弃，是把远处的东西挪到伸手可及的地方 |
| `/review` 派生专门的评审子代理 | 不做 | 我们没有 PR 这个对象。等有了再说 |
| 子代理跑完先写 `state.db` 再交付，重启后恢复重路由 | 不恢复，补一条 `lost` | 见 §10。「恢复」的前提是后台委派，v1 没有 |

## 3. 三条定死的口径

**一、子代理跑在一条独立的子会话上，有自己的 JSONL。** 不是主会话里的一段。理由在 §4。

**二、主会话里只留两样东西：那次工具调用，和一条 `agent/task`。** 形状照抄
`human/handoff` / `tool/approval`：同一个 `id` 会来多条，界面按 id 认，取最后一条
（[session/types.ts](../bot/src/session/types.ts)）。子代理干了什么，点进去看。

**三、子代理不面对人。** 它没有 `escalate_to_human`，没有 `clarify` 那类东西，问不了问题。
遇到需要人拍板的事只有一条出路：**把它写进结论交回去**，由主代理决定是当面问用户、还是
开一张转人工的单。理由是归属：一张单要挂在人看得见的会话上，而子会话在侧栏里没有位置；
就算开出来，人处理完交还的时候那条子会话早就收口了，没有任何一轮能消化它。

唯一的例外是**高风险确认**——它不是「问问题」，是一次边界表态，而且卡片开得在主会话上。
见 §6。

## 4. 为什么不把子代理的事件塞进主会话

最省事的做法是给事件加一个 `scope` 字段，子代理的事件照写进主 JSONL，读的时候过滤掉。
这条路是错的，而且是**当场就错**：

| 那里的代码 | 塞进去之后会怎样 |
|---|---|
| `const turn = history.filter(e => e.type === 'turn/start').length + 1` | 轮号被子代理的轮次顶飞。日志里第 7 轮和界面上第 3 轮是同一轮 |
| `compactionPoint`：边界必须落在 `turn/end` 上 | 子代理的 `turn/end` 也是 `turn/end`。切在那儿，主会话的一轮被拦腰截断，provider 直接拒收 |
| `toAgentMessages` | 不改就是把子代理的全部过程喂回主上下文——**和这件事要做的恰好相反** |
| `sessions.events()` 的每一个调用方 | 每一处都要学会跳过。漏一处就是一个只在有委派的会话上出现的怪现象 |

一句话：主会话的事件流是**这颗 Bot 和它主人之间的那条时间线**，塞第二条时间线进去，
所有按顺序读它的东西都要重新学一遍怎么读。

代价也说清楚，因为它是真的：**多出来的这些会话文件，有两个地方会认错人。**

1. [registry/index.ts:280](../bot/src/registry/index.ts:280) 和
   [:310](../bot/src/registry/index.ts:310)：`sessions.list().filter(s => s.botId === agent.id)[0]`。
   `list()` 按创建时间**倒序**，子会话永远比主会话新。席位重装、名册行上的 `sessionId`
   丢了的那一刻，`ensureSession` 会把一条**子任务会话**认领成这个 Bot 的长会话——从此
   侧栏里那条对话是半年前某次委派的现场。这两处必须显式跳过子会话，是落地清单里的硬项。
2. [session/gateway.ts](../bot/src/session/gateway.ts) 的索引 outbox：子会话**不上报**。
   控制面的会话索引是「这个人有哪几条对话」，不是「跑过多少次子任务」。

所以子会话在根事件上要标出来：

```ts
'session': {
  // …现有字段不动
  /** `task` = 一次委派开出来的子会话。缺省按 `main` 读（老日志都是主会话）。 */
  kind?: 'main' | 'task'
  /** 谁开的：主会话、那次工具调用、那条委派。只有 kind==='task' 有。 */
  parent?: { sessionId: string; callId: string; taskId: string }
}
```

**不动 `SESSION_FORMAT_VERSION`。** 加两个可选字段不是破坏性变更（同 `session/compact` 那条
注释的理由：老版本读到不认识的东西会跳过）。但**退化的方向要写明白**：回滚一次版本，
上面那两处过滤就没了，侧栏和索引里会冒出一批子任务会话——是「多列了几条」，不是丢东西，
方向安全，但那几条会话的标题必须自己说得清自己是什么，所以子会话的 `title` 一律写成
`子任务：<goal 的前 30 字>`。

子会话的 id 用 `t-` 前缀（主会话是 `s-`）。**但代码里不许拿前缀做判断**——事实源是根事件的
`kind`。前缀的唯一用途是运维时 `ls` 一眼能分开；拿它做判断，它迟早会和 `kind` 分叉。

## 5. 东西放在哪

| 东西 | 在哪 | 为什么 |
|---|---|---|
| 子代理的全部过程（请求头、每一步、每次工具调用） | 子会话的 JSONL | 和主会话一模一样的格式。调用链路那屏、审计、重放全都不用改，换个 id 就能看 |
| 这次委派的状态、结论、花费 | 主会话的 `agent/task` 事件 | 界面上那张卡要能从日志重建：刷新页面、换标签页、断线重连之后，一次还在跑的委派不能就此消失 |
| 结论正文（回给模型的那段） | 主会话的 `tool/result` | 它是模型下一步要用的东西，就该待在模型看得见的地方 |
| 产出的文件 | 席位的共享工作区 | 见 §7 |
| 没跑完的那些 | 内存 | 同步委派，进程一死它们本来就没了。落盘是给「后台委派」准备的，v1 没有 |

**Gateway 一个字都不用改。** 模型调用照旧走 `/v1/*`（子代理也走），代理那一侧照旧一次请求
写一行 `llm_calls`，钱自动落在同一家公司的账本上（[billing.md](./billing.md)）。会话全文
照旧留在机器上，`GET /internal/sessions/:id` 对子会话原样可用——反代那条路认的是 id，
不认 kind。

## 6. 工具：继承什么、屏蔽什么、边界怎么走

### 6.1 不是一张名单，是工具自己带的一处标注

最省事的做法是在委派这边写一张名单：这几把不给子代理、这几把要特殊处理。这条路**当天就
会过期**——内置工具集还在长（这个月刚从 `bash` 那一套换成 `file` + `terminal` 两把工具集，
`patch`、`process` 都是新的），而名单漏一条的表现是**静默的**：子代理拿到一把它不该有的手，
或者少一把它本该有的手，两种都要等到线上出事才被看见。

所以判据挂在**工具自己**身上，和 `risk` 并排（[tools/index.ts](../bot/src/tools/index.ts)）：

```ts
/**
 * 这把工具在子代理手里是什么待遇。四个问题各自独立，答哪个填哪个。
 *
 * 内置工具**必须写**（见下面那条启动断言）；`mcp_*` 不写 = 全默认。
 */
export interface ToolDelegation {
  /** 子代理有没有它。`root-only` = 只有主代理有。默认 `inherit`。 */
  mode?: 'inherit' | 'root-only'
  /**
   * 它要占一样**席位级的独占资源**，写资源的名字（今天只有 `'browser'`）。
   * 同名资源在一批委派里只发一份租约。
   */
  exclusive?: string
  /**
   * 它按 sessionId 摸的那份东西**属于这场对话**（而不是属于这次执行），
   * 所以要改摸主会话的那一份。今天只有 `history_*`。
   *
   * 判据不是「它用不用 sessionId」——那样 `todo` 也该标上，而标上就是灾难（见下）。
   */
  rebind?: boolean
  /**
   * 它会**留下**按 sessionId 记账的东西——后台进程、订阅、定时器。
   * 子代理收口时这些改挂主会话，见 §7.3。
   */
  retains?: boolean
}
```

四个问题，每一个今天都已经有真实的用户：

| 标注 | 今天是谁 | 为什么 |
|---|---|---|
| `mode: 'root-only'` | `delegate_task` | 深度定死 1（§2） |
| `mode: 'root-only'` | `escalate_to_human` | §3 口径三：子代理面前没有人。没有它，`escalateBlock` 那段提示词也跟着不加——那是在教它用一把它没有的工具，纯占上下文（[context-assembly.md §2](./context-assembly.md) 的条件加载原则） |
| `exclusive: 'browser'` | `browser_*` | §7.1 |
| `exclusive: 'desktop'` | `desktop_terminal` / `desktop_open_folder` | §7.1。同一块员工正看着的屏，并行开窗口会叠成一团 |
| `rebind: true` | `history_read` / `history_search` | §6.3 |
| `retains: true` | `terminal` | §7.3。**`process` 不标**：留下东西的是 `terminal`，`process` 只是在管它起的那几个；两把都标的话移交会跑两遍，第二遍必然空手 |
| 全默认 | `todo` | 子代理要有**自己的**清单。理由和陷阱见下面那一段 |
| 全默认 | `read_file` / `write_file` / `patch` / `search_files` / `now` / `web_*` | 它们干的事和主代理干的是同一类，没有归属问题 |
| 全默认 | `mcp_*` | 见下 |

**这张表是「今天长什么样」，不是判据。** 判据是上面那四个问题。明年多出来的第七把内置工具
不会出现在这张表里，但它必须在注册处回答完这四个问题——下面这条保证了它躲不掉。

#### 拿刚进来的 `todo` 试一遍

[todo](../bot/src/tools/todo.ts) 是这周才合进来的（[docs/todo-tool.md](./todo-tool.md)）。它按
`call.sessionId` 在 `documents` 表里存一份清单，还往会话日志里写 `todo/list`——形状和
`history_*` 像得很，而正确答案完全相反。四个问题各答一次：

| 问 | 答 | 为什么 |
|---|---|---|
| `mode` | `inherit` | 一个跑 30 步的子代理**正需要**列清单。那本来就是它的活 |
| `exclusive` | 无 | 不占席位级资源 |
| `rebind` | **不标** | 见下 |
| `retains` | 不标 | 它不留活着的东西，只留一行数据 |

`rebind` 那一格是这套标注真正的考题。**「它按 sessionId 摸东西」不是判据**——照那个判，
`todo` 会被标上，而标上的后果是：子代理一开工就**把主代理的清单整份覆盖掉**（`todo` 是整表
替换，`col.put(sessionId, next)`），人正看着的那块 dock 当场变成子任务的步骤，主代理自己的
计划无声消失。

真正的判据是那份东西**属于什么**：

- `history_*` 摸的是**这场对话**。对话只有一场，就是主会话那一条——所以重绑
- `todo` 摸的是**这次执行的计划**。子代理是一次独立的执行，它当然该有自己的一份——所以不重绑

顺带一件不用改的事：`todo/list` 事件跟着 `call.sessionId` 落进**子会话**，所以主会话上那块
dock 不会被子代理的步骤刷掉，界面一行都不用防。这不是巧合——它和上面那条判据是同一个道理，
清单属于哪次执行，事件就该落在哪条会话上。

而这块清单还顺手解决了 §13 那个「同步委派期间人只看得见一个圈」的问题，见那一节。

#### 新增一把内置工具时，漏标要立刻响

`ToolService.register` 在启动时过一道断言：**名字不以 `mcp_` 开头、又没写 `delegation` 的，
直接抛，进程起不来。**

看着很凶，但它拦的是**开发期**的错误：这件事只可能发生在有人刚写完一把新工具、第一次把席位
跑起来的那一刻，而那正是最该被拦住的时刻——生产上不可能出现，那一版早就起来过了。换成
`logger.warn` 的话，它会被启动时那几十行滚屏吃掉，然后这把工具带着一个错误的默认待遇上线。

`mcp_*` 走另一条路：**不写 = 全默认（继承、不独占、不重绑、不留东西）**。理由是我们标不了——
那些工具是远端起的，几百个，名字和语义都不归我们管；而它们的共性恰好让默认是安全的：一把
MCP 工具就是「打别人家的系统」，主代理干这件事和子代理干这件事没有区别。真有例外（某个连接
的工具会留下一个跟会话绑定的东西），那是 [connectors.md](./connectors.md) 那边加一处声明的事，
不是这里猜。

#### 子代理那张表怎么算出来

```
子代理的工具表
  = 主代理这一轮的表（toolSchemasFor 的产物，含 @ 点名的排序）
  − mode === 'root-only' 的
  − exclusive 资源没租到的（§7.1）
  − 调用方在 tools 参数里没点的（可选，只缩不放）
```

`tools` 参数**只是遮掩，不是强制**。和 [context-assembly.md §3](./context-assembly.md) 第 3 条
一模一样的道理：模型硬报一个没在表里的名字照样调得通。所以真正的拒绝必须来自 **pre-execute
短路**，判据是标注加上「这次调用的 sessionId 是不是一条子会话」，不是「schema 给没给它看」。
[tools/index.ts](../bot/src/tools/index.ts) 开头那段注释写的就是这件事，这里是它的第一个真用户。

**强制这一层同样按标注走，不按名字。** 写成 `if (name === 'delegate_task')` 的话，第二把
root-only 的工具出现时没有任何东西会提醒你这里也要改。

### 6.2 高风险确认：卡片开在主会话上

子代理没有人可问，但它能碰要审批的工具（发邮件、删文件、往外发东西）。三条路：

| 走法 | 结果 |
|---|---|
| 子代理不许碰要审批的工具 | 「把这批客户的对账单发出去」这类活整个委派不了。太狠 |
| 子会话上开卡片 | 卡片开在一条界面上根本没入口的会话里。等于永远没人点，五分钟后按拒绝收口 |
| **卡片开在主会话上** | 人看得见，能点，能改参数。选它 |

具体：`ApprovalGate` 本来就是**席位级的一个 Map**，卡片开在哪条会话只取决于 append 时给的
sessionId。子代理的调用进来时，把它换成主会话 id 即可——**换的只有事件落在哪，等的仍然是
那次真调用本身**（[policy/approvals.ts](../bot/src/policy/approvals.ts) 里那段「不是它的副本」
的注释仍然成立，人在卡片上改的参数就是子代理真正跑出去的那一份）。

顺带三件事自动对了，都值得点名：

- `scope: 'turn'`（这一轮都批准）挂在主会话上，`clearTurn` 由**主轮**的 `turn/end` 触发
  ([policy/index.ts:97](../bot/src/policy/index.ts:97))。子代理跑多久都在这一轮里，语义正好
- `policy.botOf(sessionId)` 从会话根读 `botId`——子会话根上照写同一个 `botId`，查得到
- 卡片上要多一行「来自子任务《…》」。不写的话，人看到的是一次凭空出现的发信确认，
  而他刚才只说了一句「帮我把这周的活收个尾」

**PII 闸、外发闸、浏览器黑名单不变**，它们本来就只看 `botOf(sessionId)` 拿到的那颗 Bot。

留档跟着走：那句「来自子任务《…》」同时进 `tool/policy` 的 `reason`。卡片上说了、留档里
不说的话，事后翻记录的人看到的是一次凭空出现的发信确认——而那正是最该问出处的一种。

**一处已知的粗糙。** `tool/policy` 这条留档落在**子会话**上（表态确实发生在那儿），于是
上报到控制面的那条审计行带的是子会话 id，而审计页点进去要查会话索引——子会话不在里面
（§4），这一下点开是空的。不改的理由是两条路都更糟：报主会话 id 会让「事件在哪」和
「审计说在哪」对不上；把子会话塞进索引又正好是 §4 拒绝过的事。等审计页真需要点进去的
那天，它该走 §13 那条经主会话授权的路，而不是在这里改口径。

**`ESCALATE_AFTER` 这条要关掉。** 连着被挡 3 次就改口劝转人工
（[policy/index.ts:435](../bot/src/policy/index.ts:435)）——在子会话里这句话是死路：它没有
那把工具。子会话里把它换成一句「停下来，把卡在哪儿写进结论交回去」。

### 6.3 `history_*` 钉在主会话上

隔离的代价是主代理必须把全部信息写进 `context`，而它**经常写不全**——Hermes 那份文档里
「错误做法：`goal='Fix the error'`」举的就是这个。逼主代理写一篇交底书不解决问题，只是把
失败点从「忘了说」挪到「说漏了」。

所以给子代理一把按需检索的手：`history_read` / `history_search` 照给，但它们读的是**主会话**。
这就是 §6.1 那个 `rebind: true` 标注——标了它的工具，`call.sessionId` 在进 execute 之前先过一道
`rootOf`（[tools/history.ts](../bot/src/tools/history.ts) 里那个 `sessionId` 因此不用自己改）。
子代理自己那条历史它本来就全在上下文里，读它没意义。

**重绑做在管道上，不做在工具里。** 做在工具里的话，第二把「读这条会话」的工具出现时要自己
记得也写一遍，而漏写的表现是它读回来一片空白——一个看起来像「这段历史不存在」的 bug。

这不违反隔离：隔离要防的是「全量历史进每一次子请求」，防住了；一次 `history_search` 拉回来的是
有界的几十条（那个文件里的 `MAX_ROWS` 本来就是为这件事设的），而且是它自己判断需要才拉。

### 6.4 点名继承

`@Gmail 帮我把这周的邮件整理成周报`——这正是最该被委派的一句话。点名不继承，那把连接对
子代理就**不存在**（`mentionOnly` 的连接平时不进默认表）。

所以 `mentionedIn(sessionId)`（[agent/index.ts:276](../bot/src/agent/index.ts:276)）要能顺着
`rootOf` 往上走一层。继承的作用和主代理那边一字不差：顶到表头 + 放开 `mentionOnly`。
`turnMentions` 本来就是**这一轮**的东西，而子代理整个活在这一轮里，生命周期天然对齐。

## 7. 归属：独占的资源，和子代理留下来的东西

§6.1 那四个标注里，后三个都在回答同一个问题的不同侧面：**一样东西同时只能有一个主人，
而子代理是个临时的主人。** 这一节把三条规矩写完。

### 7.1 `exclusive`：一批里只发一份租约

**浏览器是席位单例。** [BrowserService](../bot/src/browser/index.ts:119) 全局一个实例、一个
attach 上去的页面（`private sessionId = ''` 存的是 CDP 的 session，不是会话 id）。两个子代理
同时驱动它，就是两只手抢同一个鼠标：A 刚点开一个下拉，B 把页面导航走了，两边拿到的快照
都是对方的。

而且那块屏**员工正看着**（slim-desktop）。三个子代理在上面同时翻页，人看到的是一场癫痫。

规矩：**标了同一个 `exclusive` 资源名的工具，一批委派里只有一个子代理拿得到**。由调用方在
`tools` 里点名，没点名就发给批次里的第 0 条。拿不到的那几个，工具表里根本没有这一组
（**遮掩之外还有强制**：`checkBrowser` 那道谁都关不掉的闸认的是 sessionId，加一条「这条子会话
没有 `browser` 租约」）。

**租约按资源名发，不按 `browser_` 前缀判。** 这套最早只有浏览器那一组工具；席位桌面那两把
（`exclusive: 'desktop'`）就是后来照这条规矩加进来的，委派这边一行没改。将来席位上
再多一样只能有一个主人的东西（一块屏、一个串口、一个只允许单连接的客户端），它写上自己的资源
名就自动落进这套租约，委派这边一行都不用改——这正是把判据挂在工具身上而不是写成名单的全部
理由（§6.1）。

### 7.2 工作区：共享，而且是故意的

一台席位一个 `~/work`，子代理和主代理看到的是同一棵树。结论之外的产出——它写的那份报告、
下载的那个附件——就靠这个回到人手上，而 `ToolResult.files` 那条链路一个字都不用改。

代价是并发写同一个文件没人拦。**不加锁**，理由是加了也没用（两个模型商量好写同一个文件的
方式，不是锁能表达的），换成两条规矩：

- 一批并发委派的 `goal` 里必须各自划清文件范围。这句话写进工具描述，让模型自己承担
- 子代理的**草稿**写 `tasks/<taskId>/`，成品才写正常位置。中间产物撞车的概率比成品高一个量级

### 7.3 `retains`：子代理跑完了，它起的东西还活着

`terminal(background=true)` 起的进程按 **sessionId** 记账
（[tools/terminal.ts](../bot/src/tools/terminal.ts)：`procs` 里每条都带 `sessionId`，
`process` 这把工具的列表、查看、终止一律 `filter(p => p.sessionId === call.sessionId)`）。
不管的话，子会话一收口就出两件事，都不是小事。

#### 问题一：孤儿进程

子会话收口后，那条会话上还活着的后台进程**没有任何人看得见、也没有任何人杀得掉**——主代理的
`process` 列出来是空的，人在界面上也没有入口。一次「帮我把开发服务器起起来」的委派，留下的是
一个占着端口、没人认领的进程；下一次委派再起一个，端口冲突，而报错里那个「已被占用」指向的
是一个查不到的东西。

**解法：改挂，不是杀掉。**

子代理收口时，遍历标了 `retains` 的工具留下的、属于这条子会话且**还没结束**的东西，把归属
改成主会话。落到今天就是一句：`procs` 里 `sessionId === child && !endedAt` 的那几条，
`sessionId` 改成 `rootOf(child)`。**只动记账那一行，不碰进程本身**——它的 cwd 在共享工作区里
（§7.2），换个主人不影响它在跑什么。

几个定死的细节：

| | 怎么办 | 为什么 |
|---|---|---|
| 已经结束的（`endedAt` 有值） | **不移交** | 它的输出早就在子会话里了，移交过去只会让主代理的 `process` 列表里多一堆历史 |
| 子代理是被 abort / timeout 掐掉的 | **照样移交** | 被掐掉那次留下的进程比正常收口的更需要有人管——那正是没人来得及收尾的一次 |
| 移交的时机 | 写 `agent/task` 终态**之前** | 结论里要报出移交了什么，见下一条 |
| 结论里怎么写 | 追加一行 `接手的后台进程：<session_id> · <命令原文>` | 不报的话，主代理不知道自己刚接手了什么。它下一步很可能就要去 `process` 查这个东西，而它连 id 都没有 |

**为什么不是「一律杀掉」**：那样「委派去把服务起起来」这件事整个做不成，而这是委派最自然的
用法之一（起服务是脏活、长活、过程噪声大，正好该交出去）。杀掉还有个更隐蔽的坏处：子代理起
的东西可能正是主代理下一步要用的，而杀的动作发生在结论回来之前——主代理拿到「服务已启动」的
结论，去用，发现没有。

#### 问题二：在一条没人看的会话上自己开一轮

进程带 `notify_on_complete` 结束时走的是这一段：

```ts
if (agents.isRunning?.(p.sessionId) && (await agents.steer?.(p.sessionId, text, [], source))) return
await agents.send?.(p.sessionId, text, [], [], source)
```

子代理收口之后 `p.sessionId` 还指着子会话，`steer` 必然接不住（那一轮早没了），于是走
`send`——**在一条没有任何人看着的子会话上开出全新的一轮**。那一轮会真的跑起来、真的调工具、
真的花钱，而它的产出没有任何一条路回到人手上。这正是 §11 里「结果落在新一轮里」那个毛病，
只是这次连主会话都不在。

**解法：通知跟着起它的那个 agent；那个 agent 不在了，就交给它的主人。**

这句话拆成代码只改一个地方——`send` 那一跳的目标走 `rootOf`：

```ts
// steer 不变：子代理还在跑时，通知就该插进它自己那一轮，那正是 notify 的本意
if (agents.isRunning?.(p.sessionId) && (await agents.steer?.(p.sessionId, text, [], source))) return
// 接不住了：投给它的主人。子会话没有主人时 rootOf 回落成它自己，也就是今天的行为
await agents.send?.(agents.rootOf?.(p.sessionId) ?? p.sessionId, text, [], [], source)
```

**`steer` 那一跳一个字都不能改。** 子代理还在跑的时候，进程结束的通知就该插进**它自己**那一轮
——它才是起这个进程的人，它在等这个结果。改投主会话的话，主代理会收到一条关于它没起过的命令
的通知，而真正在等的那个子代理什么都没等到。

配套两件事：

- 上面 §7.3 问题一的移交做完之后，`p.sessionId` 本来就已经是主会话了，所以**绝大多数情况这条
  回退根本不会触发**。留着它是为了那个窄窗口：子代理收口和移交之间，进程恰好在这几毫秒里结束
- 落到主会话的那条消息要写清出处：「你派出去的子任务《…》留下的后台进程 `<id>` 结束了」。
  `source` 本来就是 `MessageSource`（`kind: 'plugin'`），把 taskId 挂上去即可——那个判别联合
  的注释里写的就是这个用途

#### 这两条都不是 terminal 专有的

写规矩的时候按 `retains` 这个标注写，不按 `terminal` 这个名字写。今天只有后台进程有这个性质，
但「留下一样按 sessionId 记账的东西」是个会重复出现的形状：一个订阅、一个定时器、一个还没
下载完的任务、一个打开着的远端会话。它们出现时该自动落进上面这两条，而不是等谁想起来。

## 8. 难易度定模型：每一条任务，主代理都要表态

这是委派里主代理**唯一必须自己做的判断**——不是「要不要委派」（那件事工具描述会教它），
是「这一条交出去的活，配得上哪档模型」。

`model_role` 取值和 [routines.md](./routines.md) 那边同一套（`TurnModelRole`）：

| 值 | 跑在哪个模型上 |
|---|---|
| `"daily"` | **不覆盖**，跟主代理这一轮同一个模型（管理员给这颗 Bot 单独挑过模型的话，那句挑选照样作数） |
| `"utility"` | 平台钉的那个便宜模型（`catalog.models.utility`）。平台没钉就照原模型跑并留一行日志，和 `roleModel` 现在的行为一致 |

### 8.1 它挂在**每一条任务**上，不是挂在这一次调用上

一次委派里三条任务各选各的，这是常态而不是边角情况：

```
delegate_task(tasks=[
  { goal: "把这三家的报价页各抓一份，列成 项目/单价/交期 的表",
    model_reason: "抓取加填表，格式我已经定死了，漏一行一眼能看见", model_role: "utility" },
  { goal: "把上季度那份合同里的付款条款逐条摘出来",
    model_reason: "照原文摘，不需要判断哪条重要",                   model_role: "utility" },
  { goal: "看这份新合同草稿，找出对我们不利的条款，逐条给理由",
    model_reason: "要判断什么算不利，判错了看结论看不出来",         model_role: "daily"    },
])
```

前两条是**机械活**（做法定死、做错一眼能看见），第三条是**判断活**。挂在调用上的话，
这一批只能整体按最贵的那档跑——而那正好是把「委派能省钱」这件事抹掉的做法。

顺带一条，例子里刻意让三条**互不依赖**：一批是并行跑的，所以「对着前两条的结果做判断」
那种活不能塞进同一批，它是**下一次**委派（主代理拿到前两条的结论，写进新的 `context`）。
把有依赖的东西塞进一批，结果是第三条在前两条还没产出时就开跑，然后交回一句「没拿到数据」。

### 8.2 判据：不看任务大小，看错了会不会被发现

模型很容易把「难」理解成「长」。所以判据不写「复杂/简单」，写两条能对着任务念的：

| 问 | `utility` | `daily` |
|---|---|---|
| 做法是不是已经定死了？ | 是。「读这几个文件、按这个格式列出来」 | 不是。要它自己选路子、自己权衡 |
| 做错了，看结论能看出来吗？ | 能。少了一行、格式不对，一眼就见 | 不能。一个错误的判断长得和正确的判断一模一样 |

典型的 `utility`：抓一批页面列成表、把一堆文件读一遍写摘要、按关键词找出现的位置、翻译、
把 N 个东西整理成固定格式、统计条数。

典型的 `daily`：改代码、定方案、评审（尤其是评审主代理自己刚做的东西）、多步浏览里要处理
意外弹窗的、跟外部系统打交道要判断异常怎么办的、一步错步步错的那种链子。

**边界情况一律往 `daily` 靠。** 和 `UNKNOWN_RISK` 那条同一个道理
（[tools/index.ts](../bot/src/tools/index.ts)）：拿不准的时候多花的是模型差价，赌错的时候
赔的是整条 30 步的过程加一次重做。

### 8.3 先说理由，再选档——而且理由排在前面

光有一个 `model_role` 字段，选档就是一次**直觉**：模型扫一眼任务，蹦出一个值。加一个必填的
`model_reason`，它就变成一次**判断**——因为要写出「做法定死、错了一眼能看见」这句话，就得真的
把 §8.2 那两问过一遍。

```jsonc
{
  "goal": "把这三家的报价页各抓一份，列成 项目/单价/交期 的表",
  "model_reason": "抓取加填表，格式我已经定死了，漏一行一眼能看见",
  "model_role": "utility"
}
```

#### 顺序是这个字段的一半价值

`model_reason` **必须排在 `model_role` 前面**，schema 里的顺序、工具描述里举的例子、
文档里这一段，三处一致。

模型是顺着往下写 token 的：先写理由再写结论，理由才有机会影响结论；反过来，先蹦出
`"utility"` 再补一句 `model_reason`，写出来的东西是**事后合理化**——它会为已经做出的选择找话
说，而那正是这个字段要防的东西。字段顺序在别处是审美，在这里是功能。

#### 没写理由 = 没做判断 = 按拿不准处理

`model_reason` 和 `model_role` 一样进 `required`，但两者缺失时的处理**不一样**，因为
「给个安全默认」这条路只有前者走得通：

| 缺什么 | 怎么办 |
|---|---|
| `model_role` | 按 `daily` 跑，记一行日志（§8.4） |
| `model_reason`，而 `model_role` 是 `"daily"` | 照跑，记一行日志。`daily` 本来就是安全的那一档，为它设卡只是白收一道过路费 |
| `model_reason`，而 `model_role` 是 `"utility"` | **按 `daily` 跑**，记一行日志 |

最后那一格是这条规矩的全部：**理由是 `utility` 的入场券。** 选了便宜档却说不出为什么，就
不给便宜档——它和 §8.2 最后那句「边界情况一律往 `daily` 靠」是同一条，只是这次的「拿不准」
由模型自己暴露出来了。

**不 400。** 和 §8.4 的口径一致：为一个能安全降级的字段把整次委派打回去，换来的是模型重试
一次、上下文里多一段垃圾，而降级的方向本来就是对的。

#### 理由是给人看的，不是给模型看的

一行 `utility` 单独摆在卡片上是一个**不可审的决定**：人看不出它选得对不对，只能等它跑砸。
配上那句「格式定死、漏一行一眼能看见」，人当场就判得出来——而这恰恰是最该被人看一眼的地方，
因为选错的代价是整条 30 步白跑（§8.5）。

所以理由的去向和档位一样：进 `agent/task.model.reason`（§12.2），卡片上跟在档位后面
（§13）。**但不进回给模型的那段结论**（§12.3）——那句话是主代理自己写的，原样念回去只是
占上下文。

**存结构，不存一句话。** 让主代理在正文里说明「我打算把第一件事交给便宜模型，因为……」是行不
通的：那段话会被压缩掉，而且没法和具体哪一条任务对上。理由跟着任务走，才摆得到那一行的旁边
——和 `mention` 那条注释是同一个道理（[session/types.ts](../bot/src/session/types.ts)）。

#### 一句话上限，不许复述任务

上限 80 字。写长了它会变成 `goal` 的复述——那既没增加信息，又把每条任务的开销抬上去（一批
三条就是三份）。判据本来就只有两问，两问的答案写不满 80 字。

### 8.4 为什么不是「默认 utility 省钱」

Hermes 的默认是子代理一律换便宜模型，理由是 token 大头在子代理身上。那个理由成立，
**但它的结论只在「子代理干的是机械活」时成立**——而委派出去的活里，最值得委派的恰恰是
那种过程很长的判断活。

一个便宜模型碰上多步工具循环，最可能的结局是绕不出来、撞满 `max_steps`：那 30 步里每一步都
带着完整的工具结果重发一遍上下文，烧掉的比模型差价多得多，最后还得主代理重做一遍。所以我们
不给「省钱」这个方向一个默认值，改成**每次都表态**。

### 8.5 缺了、写错了，分别怎么办

`model_role` 写进 schema 的 `required`——**它的作用是逼模型表态**，不是拿来 400 的。真正的
处理照 [routines.md §2](./routines.md) 那条已经定下的口径来，那句话原样适用：**没写的字段给
默认值，写了但不对的一律 400。**

- **没写** → 按 `daily` 跑，留一行日志。为一个能安全默认的字段把整次委派 400 掉，换来的是
  模型重试一次、上下文里多一段垃圾——而默认的那一档本来就是安全的那一档（§8.2 最后一句）
- **写了但不是这两个值之一**（`util`、`cheap`、`flash` 这类手滑） → **400**。当默认值处理的话，
  界面上、日志里、账单上全都显示按 `daily` 跑，而模型以为自己省了钱——这类「回 200 但没照做」
  正是 routines 那条口径要防的东西

`model_reason` 缺失是第三种情况，处理不一样（降级成 `daily`，不 400），见 §8.3。

### 8.6 选错了的出路

`utility` 的子代理绕不出来时，结论会是「跑到步数上限，做到这儿」（§9）。主代理拿到它之后
**原样再委派一次、把 `model_role` 改成 `daily`** 就行——它手上有第一次的结论，第二次的 `context`
比第一次还全。

**不做「中途自动升档」。** 换模型意味着这条子会话的上下文要跨模型迁移，前缀缓存整个作废
（[context-assembly.md §2](./context-assembly.md) 里算过这笔账：冷缓存那一轮 3151 token，
热的 54），而且换档的判据只能是「它看起来卡住了」——那个判断本身就不可靠。让主代理拿着结论
重来一次，判据清楚，代价可见。

### 8.7 钱

不用改任何东西（§5）：子代理的模型调用照旧走 Gateway 的 `/v1/*`，代理那侧照旧一次请求一行
`llm_calls`。

但 `agent/task` 上要带两样东西：这次委派的 **usage 汇总**，和**这一条实际跑在哪个模型上**
（`model_role` 加真正解析出来的 `provider/id`——平台没钉 `utility` 时它会回落，只记 role 的话
账对不上）。理由呼应 [billing.md](./billing.md) 的缺口 5：委派普及之后，「这个月为什么是这个数」
如果连「哪一次委派、用哪档模型、花了多少」都答不出来，那道缺口等于又开了一次。汇总从子会话的
`assistant/message` 事件累加，不新增记账路径。

## 9. 三个数：步数、条数、时间

| 闸 | 默认 | 可调 | 到顶怎么办 |
|---|---|---|---|
| 单个子代理的步数 | **30** | `max_steps` 参数，上限 = 主代理的 `maxSteps` | 收口，不是报错。结论是「跑到步数上限，做到这儿」+ 它最后说的那段 |
| 一次 `delegate_task` 的任务数 | — | `tasks` 数组，**上限 3** | 超了回 400 并说明。模型看得懂，会自己拆成两次 |
| 单个子代理的墙钟 | **20 分钟** | `SATUWORK_DELEGATE_TIMEOUT_MS` | abort 掉，`state: 'timeout'`，结论同上 |

30 步不是 120 步：一件**被单独描述清楚**的子任务要是 30 步还没做完，多半是描述错了或者它绕
进去了，再跑 90 步只是把错误做得更彻底。而主代理那 120 步要装的是「装环境、跑测试、按报错
改再跑」的整条链子，尺度本来就不一样。

墙钟这道闸 Hermes 明确不设，我们必须设：他们的委派在后台，我们的主轮真的 `await` 在这次工具
调用上，而人对着一个转圈的图标。20 分钟是按「一次真的浏览 + 分析能有多长」定的，比高风险
确认的 5 分钟宽，因为那边等的是人，这边等的是机器。

**任何一种到顶都不是失败。** 三条都按「有结论地收口」处理，把已经做到的交回去——主代理拿到
「做到这儿，卡在这里」远比拿到一句 `failed: true` 有用。

## 10. 生命周期

### 停止

人按停止 → 主轮的 `signal` → `ToolCall.signal`（[bridgeTools](../bot/src/agent/index.ts:1075) 那段
注释说的就是这个）→ 子代理 `abort()`。子会话的 `turn/end` 记 `aborted`，主会话的 `agent/task`
记 `aborted`。

**这条链子必须一路通到底。** 断在中间的表现和那段注释里写的一模一样：停止按钮按下去毫无动静，
而三个子代理还在后台跑到自己的超时。

### 换版静默

`quiesced()` 期间**不开新的子代理**（在 `delegate_task` 的执行入口判，抛
`QUIET_MESSAGE`），已经在跑的那一批照旧——它们属于正在跑的这一轮，由排空去等。

`busy().running` 自动就对了：子会话跑起来会进 `live`，管家那边看到的忙碌度包含它们
（[agent/index.ts](../bot/src/agent/index.ts) 的 `busy()`）。所以「三个子代理正在跑」的席位不会
被换版砍断——**这是白捡的，但要写进验收，因为它靠的是子会话进 `live` 这个实现细节**。

### 进程重启

子代理不恢复。子会话最后停在一个不收口的轮次上，下次读盘由 `healDanglingTurn` 补上
（[session/index.ts:227](../bot/src/session/index.ts:227)）；主会话那条 `agent/task` 停在 `running`。

所以席位启动时要扫一遍：主会话里最后一条 `agent/task` 还是 `running` 的，补一条
`state: 'lost'`。**这一条不能省**——不补的话，界面上那张卡永远转着，而人唯一能做的是怀疑
自己的浏览器。

`lost` 是一个诚实的状态：那件事做没做成，进程死的时候没人知道，事后也查不出来。写成 `failed`
是在编。

## 11. 为什么 v1 是同步的

Hermes 的委派立即返回一个 handle，对话可以接着进行。那个形状更好，但它要求一条**把结果送回
一条已经收口的会话**的路。我们有两条现成的，两条都不行：

| 现成的路 | 为什么不行 |
|---|---|
| `steer()` | 只在主轮还在跑时接得住。子代理跑完那一刻主轮多半早就收口了，投过去是**安静地丢掉** |
| `send()` 开新一轮（routines 那条路） | 结果落在**新的一轮**里。而新一轮的上下文里，主代理看不见自己当初为什么委派——那句话在上一轮，中间隔着的是它自己的收口。表现成「它突然汇报了一件没人问过的事」 |

同步则什么都不用造：`await` 在那儿，主轮的中止、步数计数、界面上那个「在跑」、计费的归属，
全都已经是对的。

代价说清楚：**委派期间这颗 Bot 不接新消息**（`isRunning` 为真，消息进队列）。20 分钟的委派
意味着 20 分钟的排队。这是 v1 明确接受的代价——排队本来就有 dock 那一行显示，人看得见
自己排在后面，而且他可以按停止。

要做后台委派，前置条件是先有「一条会话上可以有两条并行的时间线」这个东西，那是另一份文档。

## 12. 契约

### 12.1 `delegate_task`

```jsonc
{
  "name": "delegate_task",
  "risk": ["read"],                // **包装器不叠风险**，见下
  "parameters": {
    "tasks": [{
      "goal":       "一句祈使句：要它做成什么。不是话题，是完成判据",
      "context":    "它需要知道的全部：文件路径、报错原文、已经试过什么、什么算做完。它看不见这段对话",
      "deliver":    "结论里必须包含什么。可选",
      "tools":      ["read_file", "search_files"],   // 可选，在继承来的表上再缩一圈
      "model_reason": "抓取加填表，格式定死了，漏一行一眼能看见",  // **必填，且必须排在 model_role 前面**，见 §8.3
      "model_role": "utility",          // **必填**，按难易度逐条判，见 §8
      "max_steps":  30                  // 可选
    }]
  }
}
```

#### `risk` 是 `read`，不是「子代理能干什么它就是什么」

这一条上线当天就被打脸过，值得写下来。原来标的是 `["write", "external"]`，理由听着稳妥
——「它拿到的是主代理那张表，按最宽的算」。两条边界当场同时打中它：

1. **外发闸直接拦死。** `checkExternal` 判的是「这次调用打的是哪个外部系统」，而
   `delegate_task` 没有那个东西可判，只能落到函数最后那句兜底上，回一句「会访问外部系统，
   而它不在已授权的名单里」。开着 `no-external` 的 Bot **一次都派不出去**，而那句拒绝还把
   人引去模版里加授权——那儿根本没有它
2. **每一次委派都弹一张确认卡。** `needsApproval` 的规则是 external + write，于是「读一遍
   日志找原因」这种纯只读的委派也要人点头

它自己**不出席位**：开一条会话、在本机跑一个循环，没有任何东西发出去。真正会发出去的是
子代理的那些调用，而它们**每一次都单独过同一条管道**（§6.2）。叠在包装器上不是多一层保护，
是把同一件事算两遍——而算错的那一遍拦的是所有人。

这正是 [tools/index.ts](../bot/src/tools/index.ts) 开头那句话的另一面：决策要在**做出它的
那个操作**里强制执行。子代理要发一封邮件，该拦的是那次发信，不是「它被派出去了」这件事。

**只有 `tasks` 数组一种形状**，单条任务也要写成一个元素的数组。Hermes 支持平铺 `goal=` 的
简写，我们不抄：两种形状 = 两条解析路径 + 模型每次要挑一种，而省下的是两个方括号。

工具描述里要写死的三件事（这三段是提示词，但**挂在工具描述上而不是 system 里**——条件加载，
没挂这把工具的 Bot 一个字都不该看见）：

1. **什么时候用**：过程比结论长十倍时；几件互不相干的事可以同时做时；需要一份干净的上下文
   评审自己刚做的东西时
2. **什么时候别用**：一步就能做完的；需要跟人来回确认的（它问不了）；要连续操作浏览器的
   （§7）
3. **`context` 必须自足**：一句「修一下那个错」子代理完全不知道「那个」是什么
4. **`model_role` 怎么判**：§8.2 那两问原样搬进描述——「做法定死了吗」「做错了看结论看得出来
   吗」。两问都是「是」才给 `utility`，拿不准给 `daily`
5. **先写 `model_reason` 再写 `model_role`**，而且描述里举的例子也要按这个顺序写（§8.3）。
   顺序在这里不是审美：先蹦出档位再补理由，写出来的是事后合理化。没写理由的 `utility`
   会被降成 `daily`，这句也要写进描述——让模型知道偷懒的代价是什么

### 12.2 `agent/task`

```ts
'agent/task': {
  /** 这一条委派。同一个 id 会来多条，界面按它认，取最后一条。 */
  id: string
  /** 开出这一批的那次工具调用。一批 N 条共用同一个 callId。 */
  callId: string
  /** 跑在哪条子会话上。点开就是它。 */
  child: string
  /** 一批里的第几条，从 0 开始。**结果按它排序，不按谁先跑完**。 */
  index: number
  /** 原样的 goal。卡片上那一行标题。 */
  goal: string
  state: 'running' | 'done' | 'capped' | 'timeout' | 'failed' | 'aborted' | 'lost'
  /** 结论。`done` 是全文；别的态放它停下来之前最后说的那段。 */
  summary?: string
  /** 它产出的文件，路径相对工作区根。界面照 tool/result 那套渲染。 */
  files?: { path: string; name: string }[]
  /** 跑了多少步、调了多少次工具。卡片上那行小字。 */
  steps?: number
  toolCalls?: number
  /** 这一条花了多少。见 §8.7。 */
  usage?: Usage
  /**
   * 这一条实际跑在哪个模型上。
   *
   * **role 和 provider/id 都要留。** 只记 role 的话，平台没钉 `utility` 那段时间里的委派
   * 会显示成「按便宜的跑」，而它其实回落到了主模型上——账单和这行字对不上，而对不上的那几天
   * 恰恰是要查的那几天。
   */
  model?: {
    role: 'daily' | 'utility'
    provider: string
    id: string
    /** 主代理选这一档时给的理由（§8.3）。降级过就写降级后那一档的实情。 */
    reason?: string
    /** 降过级：写了 `utility` 但没给理由，或平台没钉 utility。人要看得出这一档不是主代理选的。 */
    downgraded?: boolean
  }
  at: number
}
```

**按 index 排序，不按完成顺序**——这一条抄 Hermes，理由他们没写而我们要写：模型下一句会说
「第一件事的结论是…」，而完成顺序是随机的，谁先跑完谁排前面等于让它每次都指错。

加一种事件不是破坏性变更（老版本读到不认识的 type 会跳过），不动 `SESSION_FORMAT_VERSION`。
退化方向：老席位读到它当没看见，界面上那次委派只剩一次普通的工具调用——**少一张卡，不丢正文**
（结论在 `tool/result` 里）。

### 12.3 回给模型的那段

一批 N 条，按 index 拼：

```
[1/3 done · utility · 12 步 · 3m20s] 把 gateway/src/routes 下所有 console.log 换成 logger
  结论：改了 7 个文件，共 23 处。两处在 catch 里的改成了 logger.warn（原来是 log），
  因为它们打的是失败路径。已跑 tsc，通过。
  产出：gateway/src/routes/*.ts（7 个）
  接手的后台进程：bg-3f2a · pnpm --filter gateway dev

[2/3 capped · utility · 30 步 · 8m01s] 找出昨晚定时任务失败的原因
  结论：做到这儿——确认失败发生在 routine_runs 的 claim 之后、发消息之前，席位当时
  返回 409。没找到 409 的来源，下一步应该看席位那侧同一时刻的日志。
```

`turn/end` 之前，子代理最后一条 assistant 文本就是结论。**没有文本**（撞顶时最后一步只有工具
调用）时写「没有结论」并置 `failed`——编一段摘要出来是最糟的选项。

上面第 2 条正是「档位选低了」长什么样：`utility` 撞满 30 步、结论停在半路。主代理下一步该做的
是原样再委派一次、`model_role` 改成 `daily`（§8.6）——所以**档位必须出现在这段文本里**，
不能只留在事件上：模型看不见事件。

### 12.4 子代理的 systemPrompt

在 `composeSystem` 的产物上**减一段、加一段**：

| 段 | 子代理 |
|---|---|
| Bot 提示词 | **继承**。它定义的是「这个员工是谁」，换掉等于让子代理用另一种口径干活 |
| `runtimeBlock()` | 继承（`[时间]` 那个约定照旧） |
| `webContentBlock()` | 按它自己那张工具表条件加载 |
| `escalateBlock()` | **不加**（§6.1） |
| Skill 正文 | **继承**，可用参数缩。Skill 是「这家公司怎么做这件事」，缺了它子代理会用通用做法做完——结论看起来对、口径全错，而那比多花几千 token 贵 |
| `taskBlock()` **新增** | 你是子代理；你**问不了人**，卡住就把卡在哪儿写进结论；工作区和主代理共享，草稿写 `tasks/<id>/`；结论怎么写（§12.3 那个形状）；`history_*` 读的是主对话；**你起的后台进程会在你收口时交给主代理，所以要在结论里点名**（§7.3） |

## 13. 界面

主会话里那次工具调用渲染成一张卡（一批 N 条 = 一张卡 N 行）：

- 每行：状态点 + `goal` + 档位（`utility` 那档要标出来）/ 步数 / 耗时 / 花费
- 档位后面跟那句 `model_reason`，一行小字。**这是档位可不可审的全部**：光一个 `utility`
  人判不出选得对不对，配上「格式定死、漏一行一眼能看见」当场就判得出来（§8.3）。降过级的
  （`downgraded`）要标出来，否则人会以为那一档是主代理选的
- 跑着的时候实时更新（`agent/task` 的 `running` → 终态，走已有的 SSE，界面按 id 取最后一条）
- 结论默认折叠，展开是 §12.3 那段
- 行尾一个「看过程」→ 子会话的只读回放，**摊开在卡片里**（不是另开一屏）。它取的是子
  会话全文，而**这条路要经主会话授权**：子会话不进控制面的会话索引（§4），而 Gateway 的
  `seatTargetForSession` 查的正是那张索引——按子会话 id 直取 `/runtime/sessions/:id/history`
  换回的是 503，而那个 503 在界面上长得像「席位掉线了」。所以另开一条
  `GET /runtime/sessions/:id/tasks/:child/history`：`:id` 是主会话（Gateway 认得它），
  父子关系由席位那头核对（它才有 JSONL）——不核对的话，这条路等于「拿任意一个 id 就能读
  这台席位上任意一条会话」
- **摊开才去取**：那是一跳打到席位的请求，而多数时候人只想看结论。取过一次就不再取
  ——委派是同步的，卡片摊开时那一条早就收口了，没有「刷新看看新的」这回事
- 产出文件照 `tool/result.files` 那排药丸渲染

### 跑着的那几分钟，人得看得见它在干什么

同步委派最难受的地方在 §9 和 §11 都提过：主轮真的 `await` 在那儿，最长 20 分钟，而人对着一个
转圈的图标。步数和耗时能动，但那两个数说不出**它做到哪了**。

刚合进来的 `todo`（§6.1）正好补上这一格：子代理的清单落在子会话里，那张卡上多一行进度就够了。

- 卡片每行右侧：`3/7`，外加当前那条 `in_progress` 的原话，一行截断
- 数据从哪来：子会话的 `todo/list` 事件（全量快照，取最后一条），或者
  `readTodos(ctx, childSessionId)`——两条路都是现成的，一行不用新写
- **不做的**：不把子代理的清单画成主会话那块 dock。那块 dock 是主代理自己的计划，被子任务的
  步骤挤掉就是 §6.1 里那个「无声消失」的翻版，只不过发生在界面上而不是存储里

子代理没列清单时这一行不出现（多数短任务不会列）——**不编一个假的进度出来**，那比没有进度更
糟：人会按着那个数去估还要多久。

`/agents` 那种全局浮层（Hermes 有）**不做**：v1 是同步的，同一时刻只有一批在跑，而它就在
对话里摆着，再开一个浮层去看同一件事是白加一屏。

侧栏那颗状态点在委派期间是「在跑」，和普通一轮没区别——**这是对的**，人要知道的是「它在忙」，
不是「它开了几个分身」。

## 15. 验收

1. **上下文真的省下来了**：一次「翻日志找原因」的委派跑完，主会话新增的 token 是结论那几行的
   量级，不是过程的量级。对着 `request/header` 的 `sections` 量下一轮
2. **隔离是真的**：子代理的 systemPrompt 里没有主对话的任何一句话；它调 `history_search` 能搜到
3. **并发按 index 回**：三条任务，让第 3 条最快跑完，回给模型的仍然是 1/2/3 的顺序
4. **停止一路通到底**：三个子代理跑着时按停止，三条子会话的 `turn/end` 全是 `aborted`，
   进程里没有任何东西继续在跑
5. **审批开在主会话上**：子代理发一封邮件，卡片出现在主对话里、写着来自哪个子任务、改参数
   之后发出去的是改过的那一份。**已覆盖**：`bot/e2e-guards.mjs` 的 `delegation` 组，14 条
   ——含「子会话上不开卡片」「用主会话 id 点得动」「主代理批过这一轮子代理不再问」
   「子任务收口不清主会话名单，主轮收口才清」
6. **深度封死**：给子代理硬报一个 `delegate_task`（绕过 schema），被 pre-execute 挡下并留一条
   `tool/policy`
7. **认领不认错**：删掉名册行上的 `sessionId` 重启，`ensureSession` 认回来的是主会话，不是最近
   那条子会话
8. **重启之后没有永远转着的卡**：委派跑到一半 `kill -9`，重启后那张卡是 `lost`
9. **换版等得到它**：委派跑着时管家发排空，席位报 `busy().running > 0`，不被重启
10. **钱对得上**：一次带两条子任务的委派之后，`usage_charges` 上多出来的行数 = 主代理 + 两个
    子代理的模型调用次数，一行不多一行不少
11. **一批里各跑各的档**：一次委派三条，两条 `utility` 一条 `daily`，三条子会话的
    `request/header` 里是两个便宜模型 + 一个主模型；`agent/task.model` 上三条各自对得上
12. **档位的三种错法分开**：`model_role` 不写 → 按 `daily` 跑并留日志（不 400）；写成 `util`
    → 400，整次委派不发生；写了 `utility` 但没给 `model_reason` → **降成 `daily`**，
    `agent/task.model.downgraded` 为真，卡片上标出来
12b. **理由排在前面**：工具 schema 里 `model_reason` 的字段顺序在 `model_role` 之前，
    工具描述举的例子也是这个顺序（§8.3）。这一条靠读 schema 验，不靠跑
13. **平台没钉 utility 时不撒谎**：把目录里的 `utility` 清空，选 `utility` 的那条照原模型跑，
    而 `agent/task.model` 上记的是**真正跑的那个** provider/id，不是 `utility`
14. **后台进程不留孤儿**：子代理 `terminal(background=true)` 起一个长跑进程然后收口，主代理
    的 `process` 列表里**看得见它**，结论里也报了它的 `session_id`，人能从界面上把它杀掉
15. **通知不会在暗处开一轮**：子代理收口**之后**它起的进程才结束，那条通知落在**主会话**上，
    子会话上不多出任何一个 `turn/start`
16. **但子代理还在跑时通知不改道**：同一个进程改成在子代理跑着的时候结束，通知 steer 进
    **子代理自己**那一轮，主会话上什么都不多
17. **漏标就起不来**：给任意一把内置工具去掉 `delegation` 标注，席位启动直接抛，错误里点名
    是哪一把。**这一条要写成单测**，它是「将来新增工具不会静默走错边」的全部保障

e2e 走 `e2e/` 现有那套（跟 `e2e/routine-model.mjs` 同一个形状）：1、3、4、6、8 可以自动化，
其余人工过一遍。

## 16. 这一版不做的

- **后台委派**（立即返回 handle）。前置条件见 §11
- **深度 > 1** 和 `role: "orchestrator"`
- **跨席位委派**：把活交给同事的那颗 Bot。那要过 Gateway、要跨账号授权、要另一套计费归属，
  是另一份文档
- **子代理开转人工单**（§3 口径三）
- **`/review` 那样的专用评审子代理**。等有了 PR 这个对象再说
- **子代理之间通信**。它们只通过工作区和各自的结论说话
- **持久化恢复**。同「后台委派」
- **`/agents` 全局浮层**（§13）
